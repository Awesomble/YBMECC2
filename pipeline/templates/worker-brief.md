## 전달할 최소 계약

파일 소유권, 표시 초 시작/끝, 핵심 발화의 실측 시각과 자막·화면 강조, 동작 정점(`[대상]+[동작 이름]+[방향·경로]+[실측 어절 시각]` — 「역동적으로」 같은 형용사만으로 주지 않는다, `docs/11-motion.md`)·효과음 동기화 지점과 읽을 정착, 시작→결과 상태, 사용하는 실제 에셋, 앞뒤 객체/전환, 장면 간 공통 시각 체계(제목·키커·라벨 처리)와 프로젝트의 승인된 디자인 방향 위치를 전달한다. 아래 상세 절은 해당 작업에서 필요한 것만 읽는다. 워커마다 테마·서체를 다시 고르거나 긴 브리프·중복 기획을 복제하지 않는다.

전달 자료는 담당 소스·스토리보드와 관련 절 발췌로 한정한다. 이미 제공한 발췌를 원문 전체로 다시 읽지 않는다. 완료 시 변경 파일·핵심 차이·실제 검사·남은 문제만 반환하고 대본/소스/명령 출력을 되풀이하지 않는다. 필요한 계약이나 자산이 빠졌으면 추측 구현 대신 그 누락을 알린다. 사용량 절감은 구도·주연 동작·정보 정확도·최종 검수를 낮추는 근거가 아니다.

**ABMEN 품질 계약:** `docs/channel/05-brand-pipeline.md` §3-1의 필요한 절을 패킷에 포함한다. 1편의 간결한 구성·2편의 행동으로 설명하는 모션을 적용하며 `이번 블록의 새 이해 | 주연의 변화 원인과 전후 상태 | 이전/다음 장면의 객체·비교축 | 동시에 바뀔 값·단위·대상 | 자막/화면·전환/보조 그래픽/소리의 강조 계약 | 등장·정점·정착과 중간 프레임 위험 시각`을 전달받는다. 값만 먼저 교체해 옛 단위를 남기거나 소재 이동 중 핵심 가격을 가리지 않는다. 연결 계약이 없으면 카드별로 임의 설계하지 말고 메인에게 누락을 알린다. 결과에는 구현한 상태 변화·강조와 검수가 필요한 시각을 짧게 반환한다. root 자막·오디오가 메인 소유이면 워커가 중복 구현하지 않고 필요한 강조 시각과 대상을 반환하며, 메인이 실제 root에 조립해 확인한다. 기법·거리·정지 시간 할당량을 만들지 않는다.

화면/음성 분리는 기술적 트랙 소유권이다. 의미와 동작의 시간 분리가 아니다. 포스터 승인 후에도 카메라·피사체 크기·정보 공개 순서는 연출한다. 무대 래퍼 전체를 overflow:hidden/clip-path로 봉쇄하지 않는다. 전체 캔버스 안에서 경계 돌파를 구현하고 작은 락업/자막 오버레이의 가독성을 확인한다. 전용 상하 밴드는 복구하지 않는다. 사진과 그래픽이 주역이므로 대표 동작의 강도와 상태 변화를 먼저 확인한다.

## ① 이징 — `powerN` 은 `t^(N+1)` 이다

GSAP 규약: `power1`=quad · `power2`=cubic · `power3`=quart · `power4`=quint.
**경계 속도 계수는 N 이 아니라 N+1.**

```
powerN.in   종단(t=D) 속도 = (N+1)·d/D
powerN.out  진입(t=0) 속도 = (N+1)·d/D
```

| 이징 | t=0 | t=D | 컷 경계 |
|---|---|---|---|
| `power2.in` / `.out` | 0 / **3** | **3** / 0 | ✔ |
| `power3.in` / `.out` | 0 / **4** | **4** / 0 | ✔ |
| `power4.in` / `.out` | 0 / **5** | **5** / 0 | ✔ |
| `expo.out` | 6.93 | 0 | ✔ |
| `back.out(1.7)` | 4.70 | 0 | ✔ |
| `sine.out` | 1.571 | 0 | ✔ |
| `none` | 1.0 | 1.0 | ✔ |
| `powerN.inOut` | 0 | 0 | ✘ 정지→정지. 관통 컷엔 부적합 |
| `elastic.out` | — | **4057** | 실제 경계 구간/진동을 확인 |
| `circ.out` | **4472** | — | ✘ 수직 접선 |

- **차수가 같으면 계수가 약분된다** — `power4.in → power4.out` 은 4로 풀든 5로 풀든 같은 `D` 가 나온다.
  어긋나는 건 차수가 다른 이음매뿐 (`power3.in→power4.out` 이면 +6.7%)
- 🔴 **이 오류는 렌더러 잡음처럼 보인다.** 00003 에서 워커 둘이 「리샘플링 잔차 26~35%, 원인 미상」으로
  두 번 닫았다가 되열었다. **모델과 실측이 안 맞으면 도구를 의심하기 전에 이징 차수부터 확인하라.**
  진단법: `powerN` 이 안 쓰인 구간(선형·`sine`·`expo`)에서 오차가 사라지면 도구가 아니라 네 모델이다
- **차수 판별은 렌더된 프레임 수열로.** 프레임 0 만 보면 어느 차수든 `d` 에서 출발해 구별이 안 된다 — **최소 3프레임**

## ② 측정 표준 — 값만 주지 마라

```
전경 판정   tol N = (|Δr|+|Δg|+|Δb|)/3 >= N        (기본 tol 12)
그라운드    영상 전체의 최빈색                       ← 팔레트 상수를 박지 마라
제외 밴드   하단 밴드 y>=1360 (자막 ≤2줄) · 상단 밴드 y<360 (좌상단 로고 x80·y228·높이 112 — 2026-09-27 이전 편은 텍스트 락업 x80·y238·w304·h46). 측정에서 빼는 구역일 뿐 화면 구성이 아니다 — 배경은 1080×1920 풀화면이다.
            **정보 정착은 x60~960 · y360~1360**. 56px 안쪽 여백은 기본 배치 제안이다. 진입·퇴장·통과는 자유 (docs/09 §1)
```

**수치를 남에게 줄 때 반드시 함께 적는다 — `crop` · `스케일` · `양자화` · `tol` · `비교연산자` · `측정 시각(mtime/판번호)`.**

00003 에서 이걸 빠뜨려 **사고가 세 번** 났다. 세 번 다 **값은 맞았고 자가 달랐다**:
① 두 워커의 `tol` 정의가 달랐다 ② 한쪽은 풀해상도, 한쪽은 1/8 — 30~100배 차이
③ 「전체 프레임·정확 RGB」로 잰 값을 「crop·192×214·4비트 양자화」 임계와 맞댔다

그 외 반드시 지킬 것:

- 🔴 **그라운드를 화면에서 샘플링하지 마라** — 요소 위를 짚는다. 배경은 고정값으로 정하고 시작한다
- 🔴 **밴드는 물체 경계가 아니라 여백에서 자른다.** 구간 **양 끝 프레임 모두**에서 여백이어야 하고,
  밴드 안에 정지 요소가 없어야 한다. 좌표만 적으면 틀린 합의가 성립한다
- 🔴 **컷에 맞닿은 스텝끼리** 비교한다 — `앞의 마지막` ↔ `뒤의 첫 스텝(0→1)`. 한 칸 밀리면 7배 벌어진다
- 🔴 **이음매는 조립본에서 잰다.** 격리 하네스로 남의 프레임을 재면 값이 달라져 상대를 틀렸다고 지목하게 된다.
  자기 프레임의 **안쪽**만 격리에서 판단하라
- 🔴 **방향 일치가 유일한 정량 기준이다.** 크기는 추정기에 따라 0.50~1.76 배로 흩어진다 — 참고 기록으로만
- 🔴 **화소는 무엇이 그렸는지 모른다.** 시각·순서·인과는 **소스의 트윈 시각**에서 읽어라.
  「글리프가 나타난 시각」을 화소로 추정하다 거짓 경보가 났다 — 그 화소는 페이드 중인 이월이었다
- **「같은 파일인데 다르다」고 말하기 전에 두 산출물의 mtime 을 비교하라.** `stat` 한 번이면 끝난다

## ③ 보고 — 이 스키마로만

보고는 **대화로 간결하게 전달한다.** 필요한 임시 측정 자료만 세션 스크래치패드에 둔다(저장소에 두지 않는다). 00003 에서 보고 63건이 중앙값 3,502자였고,
그게 팀리드 컨텍스트에 영구히 쌓여 74K → 721K 로 부풀었다.

```
md5 <앞8자> · mtime <HH:MM:SS>

판정
  <기준>            <측정값>   <통과/실패>
  ...

변경
  <항목>            <픽셀 영향 O/X>
  ...

필요한 근거 → 대화의 측정값·실제 화면/시각 (임시 자료가 있으면 /tmp 경로)
```

- **픽셀 영향 O/X 를 반드시 표시한다.** 주석만 바뀐 것이면 재렌더가 필요 없다
- 지시와 다르게 간 판단은 **근거와 함께** 보고하라. 00003 에서 그런 보고가 여럿 나왔고 **전부 워커가 옳았다**
- 팀리드가 준 기준이 틀렸다고 보이면 **맞추려 들지 말고 반박하라.** 실제로 두 번 그랬고 두 번 다 맞았다

## ④ 동결 — 「완료」는 동결이 아니다

워커에게 완료는 *"이 라운드 지시를 처리했다"*, 팀리드에게 완료는 *"이 바이트를 구워도 된다"* 다.
00003 에서 이 어긋남으로 **사고가 다섯 번** 났고 한 번은 사용자에게 옛 판이 나갔다.

1. 보고에 **md5·mtime** 을 적는다
2. 보고 이후 **파일을 열지 마라.** 읽기는 되고 쓰기는 안 된다
3. 추가 결함을 찾으면 **고치지 말고 글로만** 보고한다
4. 팀리드가 **「지금 `<md5>` 로 굽는다, 맞나?」** 를 물으면 예/아니오로만 답한다.
   그 물음 전까지는 새 지시에 따라 고쳐도 된다
5. **편집 없이 측정만 이어지면 스스로 종료하라** — 발견한 것을 글로 남기고 끝낸다.
   00003 에서 한 워커가 파일 확정 뒤 **143분(가동의 65%)** 을 측정 논쟁으로만 돌았다

⚠️ 팀리드에게: **새 작업 지시와 동결은 양립할 수 없다.** 새 수정을 시키면서 "동결 규약은 그대로"를
붙이면 워커는 「고치고 → 보고하고 → 다시 동결」로 읽는다. 합리적인 독해다. 둘 중 하나만 보내라.

🔴 **팀리드에게 둘째 — 시킨 일을 내가 하려면 「그만해라」를 먼저 보내라** (2026-09-11 · 00008).
워커가 안 움직이는 것 같아 **같은 파일을 내가 직접 고쳤고, 워커에게 취소를 안 알렸다.**
워커는 뒤늦게 깨어나 **내 수정 위에 제 수정을 얹었고**, 나는 그 중간 상태로 구웠다.
감독이 `render-gate` ①에서 잡았다 — 봉인 지문 `160aeb61…` ≠ 현재 `51917bd2…`.

> *"렌더와 소스가 어긋나면 프레임을 뽑아 봐도 그게 최신인지 알 수 없어 **심사 자체가 무효**가 된다."*

감독은 F22 를 **아예 보지 않고** 반송했고, 그게 옳다. 렌더 한 번(90초)과 심사 한 라운드를 버렸다.

- **한 파일에 두 사람을 붙이지 마라.** 워커가 느려 보이면 재촉하거나 회수하되 **둘 중 하나만** 한다
- 회수할 땐 **「그 작업 중지. 내가 잡는다」를 명시**한다. 조용히 가져가면 충돌한다
- 🔴 **굽기 직전·직후에 대상 파일의 md5 를 직접 찍어 같은지 확인해라.** 이번엔 그렇게 해서
  `b132cc28 → b132cc28 불변` 을 확인하고 넘겼다. `hf-render.sh` 가 봉인은 하지만
  **어긋났다는 사실은 감독 단계에 가서야 드러난다** — 그 전에 내가 잡는 게 싸다

⚠️ 이 사고는 반대 방향으로도 난다 — **팀리드가 워커 동결본을 통지 없이 고치는 것**(00006).
아래 「동결 확인에 답할 때」 절이 그 경우다. **양쪽 다 원인은 하나: 소유권을 말 안 하고 옮긴 것.**

## ⑤-0 배치 검산 — 충돌 위험 정보와 소재의 관계

ABM 00018의 가격택·고기·저울 겹침은 크기·깊이 관계를 설계하지 않은 사고였다. **그리기 전에 같은 시간에 읽힐 정보와 가까이 지나는 소재**의 `요소 | x | y | w | h | 정착 구간`을 확인한다. 모든 장식을 표로 작성하는 의무가 아니라 정보 가림을 예방하는 검산이다.

```
겹침 후보 = (x1 < x2+w2) ∧ (x2 < x1+w1) ∧ (y1 < y2+h2) ∧ (y2 < y1+h1)
```

교차한 쌍은 레이어·시각·의도를 대조한다. 사진 위 라벨·마스크·겹쳐 쓰기는 허용하고 **읽을 정보가 의도치 않게 가려지거나 잘릴 때** 경로·위치·시간을 고친다. 산술은 실제 root의 등장·확대 정점·정착 검수를 대신하지 않는다. 보고용 파일은 만들지 않는다.

무대 로컬 1080×1000, 정보 정착 x60~960·y0~1000을 따른다. 여백 56px·행 간 24px·열 간 40px는 시작점일 뿐 구도 의무가 아니다. 사진을 받침에 놓으면 접점·깊이를, 용기에 담으면 크롭 의도와 남길 정보를 확인한다. 사진 크기 하한·받침 배율·아이콘 개수로 판정하지 않는다. 제목·가격표가 사진의 핵심 부위를 덮으면 글자를 덜거나 장면을 재구성한다.

## ⑥ 🔴 `audio_meta.json` 의 온셋을 그대로 믿지 마라 (2026-09-10 · 워커 5명 실측)

**읽기 범위:** 아래는 ABM 한국어 음성의 경계 판독 이력이다. 영어의 모든 컷을 세 추정기로 재측정하라는 기본 절차가 아니다. ABMEN은 video ③의 승인 대본·실제 청취·발화 실측을 적용하고, 핵심 강조의 경계가 어긋나거나 불명확할 때 이 절의 해당 원인을 확인한다. 과거 +0.13초 편차나 음소 지문을 다른 화자·언어에 일괄 보정하지 않는다.

**ABMEN 영어 실측(2026-10-08 · 00069·00076 — pitfalls §186):** 방향은 아래 ABM과 같다(whisper가 실제보다 이르다). 폭은 더 크다 — 2인 대화의 **화자 전환·쉼 뒤 첫 어절**이 0.2~0.47초(00076 cut-08 'Does' whisper 5.04 → 실측 5.51, cut-01 'exam' 2.06 → 2.22). 규약: ① 메인이 준 실측 온셋을 쓴다. 없으면 `silencedetect=noise=-36dB:d=0.11`로 그룹 시작을 재고 20~40ms RMS 포락선으로 검산한다 ② **그룹의 첫 어절만** 옮긴다 — 줄 전체를 밀면 중간 어절이 늦어진다(00069: 공유 8.17 vs 실측 7.70, 워커가 잡았다) ③ 쉼 뒤 탐색은 0.7초까지 ④ 쉼표·콜론 뒤 쉼과 자음 폐쇄는 어절 시작이 아니다. 아래 ABM 절의 세 추정기·음소 지문은 경계가 불명확할 때만 쓴다.

`transcribe.py` 는 **whisper-small** 을 쓴다. 그 어절 시작 시각은 **문장 뒤로 갈수록 이르게 누적된다.**

| 00006 F09 실측 편차 | 올리면 | 차이가 | 커집니다 |
|---|---|---|---|
| meta vs 실측 | −0.2f | **−4.3f** | **−5.1f** |

컷머리도 이르다 — F16·F19·F20 에서 각각 +0.125 / +0.205 / +0.125 초.

**규약**
- 자막 클립 경계는 `audio_meta` 값을 **정본으로 그대로 쓴다**
- 🔴 **임팩트·큰 숫자·페이오프 착지는 `.media/audio/frame-NN.wav` 를 직접 재라**
- 추정기 **하나로 정하지 마라.** 셋을 대조해 수렴하는 값을 쓴다:
  ① whisper-medium (프레임을 **이어 붙여** 정렬 — 경계에서 첫 어절이 0 으로 클램프되는 걸 없앤다)
  ② RMS 포락선 (25ms 창 / 10ms hop)
  ③ 음절 등간격 (발화 구간 ÷ 음절수 — 앞뒤 ms/음절이 맞는지로 검산)

⚠️ **포락선의 깊은 골이 곧 어절 경계는 아니다.** 마찰음 ㅅ·폐쇄음 ㅂ 이 같은 깊이의 골을 만든다.
00006 에서 워커가 −50dB 골을 구절 경계로 읽었다가 등간격 모형과 대조해 **「백」의 /p/ 폐쇄**임을 알아냈다.

## ⑤-b 🔴 착지 규약 — 「끝」이 아니라 「정점」이 온셋에 온다 (2026-09-10 판정)

**문서와 납품본이 엇갈려 워커가 물어왔다.** `docs/11-motion.md` 는
「강조 애니메이션이 *끝나는* 프레임 = **강세 음절**」이라 쓰는데, 00003 납품본은 온셋에서 **시작**한다.

원인: **우리에겐 강세 음절 데이터가 없고 어절 온셋만 있다.**
그래서 「끝 = 강세」가 「끝 = 어절 온셋」으로 구현됐고, 그러면 **시각 사건이 소리보다 통째로 먼저 끝난다.**
00003 은 그 반대편으로 갔다. 정답은 가운데다.

```
attack 0.10s  →  ★정점 = 어절 온셋  →  정착 0.20s     (총 0.30s)
```

### 🔴 무엇이 「그 어절」인가 — 발화 개시가 아니라 **그 값을 말하는 어절**이다

00006 실측 사례. 「값은 백구십구만 원부터고」에서
- ❌ 발화 개시(0.34 「값은」)에 맞추면 → **「값은」에서 터진다**
- ✅ 숫자 어절(0.710 「백구십구만」)에 맞춰야 → 옆 프레임의 「백칠십만」과 **대조가 성립한다**

> **불변량은 「발화 개시」가 아니라 「펀치 정점 = 값 어절 개시」다.**

⚠️ 온셋 값 자체는 §⑥ 대로 **직접 재라.** `audio_meta.json` 은 문장 뒤로 갈수록 이르다.

### 🔴 어절이 2~3개뿐인 짧은 프레임이 가장 위험하다 (2026-09-10 · W2 실측)

whisper 가 **앞 무음을 첫 어절에 통째로 먹인다.** 그리고 그 앞 프레임에서 경계 어절이
안 넘어오면, **다음 프레임의 첫 온셋이 그 어절 길이만큼 앞당겨진다.**

00006 실증: 「판매는」(파형 0.00~0.31)이 오인식(「반면은」)으로 F4 꼬리에 남자,
F5 의 「18일에」가 **0.325 → 0.153 으로 172ms 당겨졌다.** 172ms ≒ 「판매는」의 길이다.
**두 현상은 같은 원인이다.**

`hf-audio.mjs` 가 어절 3개 이하 프레임을 🔴 로 찍어 준다. 그 프레임을 맡았으면 **반드시 직접 재라.**

```bash
ffmpeg -v error -i .media/audio/frame-NN.wav -f s16le -ac 1 -ar 16000 /tmp/o.raw -y
node <저장소>/pipeline/lib/onset-env2.mjs /tmp/o.raw <t0> <t1>   # 5ms hop · 20ms 창 dBFS 포락선
~/.venvs/abm-whisper/bin/python <저장소>/pipeline/lib/onset-wh.py .media/audio/frame-NN.wav
```

⚠️ **경계는 「에너지 골」로 잡는다.** 00006 실측 예:
`0.670~0.710 골 −33.3dBFS ← 「백」 파열 폐쇄 → 0.710 −28.1 → 0.760 −12.0 정점`
audio_meta 의 0.640 은 「은」 모음 한가운데(−19.8dBFS)로 **경계가 아니라 모음 안**이었다.

### 🔴 「추정기 셋이 일치」가 거짓일 수 있다 — 등분과 whisper 는 독립이 아니다 (2026-09-10 · W7 자기 발견)

**음절 등분과 whisper 는 둘 다 `t≈0` 앵커에 매달려 있다.** 앵커(발화 시작)가 틀리면
**나란히 틀리면서 서로를 검증한 것처럼 보인다.**

00006 실증. F19 에서 whisper 0.600 과 등분 0.607 의 일치를 근거로 채택했는데 **가짜였다**:

```
등분이 발화 시작을 0.000 으로 잡았다. 그런데 F19 의 0.000~0.180 은 −31~−42 dBFS —
피크 −13.7 대비 −17~−29 라 **발화가 아니다.** 실제 시작은 0.205.

앵커 정정 → (1.820−0.205)/12음절 = 0.1346 s/음절 → 「오백구만」 = 0.743
교차 확인    골 0.730/−44.2 → 상승 0.735  ·  플럭스 피크 0.775
⇒ 0.735 / 0.743 / 0.775 일치.  whisper 0.600 은 0.14 이르다
```

**규약**
1. 🔴 **앵커(발화 시작)를 프레임마다 따로 재라.** 00006 다섯 프레임이 전부 달랐다 —
   F16 0.140 · F17 0.040 · F18 0.105 · F19 0.205 · F20 0.000
2. 등분을 쓸 때는 **앵커를 명시**하고, 그 앵커가 −30dBFS 기준 발화 구간인지 확인한다
3. 🔴 **독립성을 따져라.** 「셋 중 둘이 일치」를 근거로 쓰기 전에
   **그 둘이 같은 가정을 공유하는지** 보라. `t=0` 을 공유하면 하나짜리 증거다
4. 진짜 독립인 것: **스펙트럴 플럭스 피크**·**RMS 골** — 이들은 앵커를 안 쓴다

### 🔴 정정 — 「등분과 whisper 는 독립이 아니다」는 **절반만 맞다** (같은 날 W2 반박)

둘은 **서로 다른 것에 매달린다.** 그래서 서로가 서로를 잡을 수 있다:

```
(a) 앵커 오류          → 등분이 통째로 밀린다.  **whisper 가 잡는다**   ← 00006 F19
(b) 내부 경계·귀속 오류 → whisper 만 밀린다.    **등분이 잡는다**       ← 00006 F05
```

F05 는 **앵커가 맞았는데도** whisper 만 172ms 틀렸다 (첫 90ms 가 −15.2 dBFS 로 무음이 없다).
원인은 **어절 귀속**이었다 — 「판매는」이 앞 프레임 꼬리에 남아 F05 첫 자리가 비었고,
당겨진 172ms 가 「판매는」의 실측 길이(0.00~0.31)와 일치한다.

> **정확한 형태: 「앵커를 dBFS 로 못박은 뒤에야 등분과 whisper 가 진짜 독립이 된다.」**
> 등분은 **버릴 도구가 아니라** whisper 의 내부 경계를 검증하는 유효한 제2 추정기다.

### 🔴 등분의 앵커는 **양 끝**이다

끝점을 무엇으로 잡느냐로 갈린다. 00006 F05 실측:

| 끝점 | 「18일에」 / 「시작합니다」 | 실측 대비 |
|---|---|---|
| 프레임 길이 1.325 | 0.331 / 0.773 | **+6ms / +43ms** (꼬리 무음만큼 늦다) |
| 발화 끝 1.190 | 0.297 / 0.694 | **−28ms / −36ms** (문장 종결 늘어짐만큼 이르다) |
| **실측 (dBFS 골 + 플래토)** | **0.325 / 0.730** | — |

**진실은 둘 사이에 있다.** 한쪽이 잘 맞았다면 **두 편향이 상쇄된 우연**일 수 있다 —
F05 에서 +6ms 로 맞았던 방법이 F19 에서는 0.14초 틀렸다.

⚠️ W7 은 이 프레임을 **세 번** 고쳤다 (0.620 → 0.605 → 0.740).
중간의 0.605 는 「제 오독을 정정한다」며 자신 있게 보고한 값이었고, **그게 오히려 틀렸다.**
원래 플럭스 판독(0.775)이 맞았다. **자기 정정이 항상 개선은 아니다 — 정정에도 근거를 요구하라.**

### 🔴 스펙트럼 지문으로 「소리의 정체」를 가려라 — 시각만 재면 들숨 위에 펀치를 건다 (2026-09-10 · W1)

00006 F01 꼬리(1.52~1.80)에 −52dB → −22dB 로 완만히 오르는 소리가 있었다.
포락선만 보면 **다음 어절의 시작으로 읽힌다.** `audio_meta` 도 F02 「십팔 프로,」를 0.000 으로 적었다.
**그대로 썼으면 가격 펀치가 들숨 위에서 터졌다.**

**방법 — 같은 영상 안에서 확인된 음소를 기준 지문으로 삼는다**

```
frame-21 「십팔」 /ɕ/ (확인된 마찰음)   고역>3k 0.78~0.89 · 저역150-900 0.007~0.03
frame-02 0.14~0.22                     고역 0.83~0.88 · 저역 0.010~0.017   → 일치 ⇒ 「십」
frame-01 1.52~1.76                     고역 0.33~0.45 · 저역 0.14~0.32
                                       centroid 3.1~3.9kHz                → 불일치 ⇒ 들숨
```

- **마찰음(ㅅ·ㅊ)**: 고역 에너지 압도적, 저역 거의 없음
- **들숨**: 고·저역이 함께 중간값, centroid 가 어중간
- **비음(ㄴ·ㅁ)**: 저역 지배, centroid 1200~2000Hz — 🔴 **골 바닥이 아니라 유성 재개시가 온셋이다**
  (F21 「이십구만」에서 −39.8dB 골을 경계로 읽을 뻔했다. 실제로는 「프로**는**」의 /n/ 이었다)

**규칙**
1. 온셋 후보 구간이 나오면 **그게 무슨 소리인지** 먼저 가려라. 시각만 재지 마라
2. 기준 지문은 **같은 영상의 확인된 음소**에서 뽑는다 — 화자·마이크·배속이 같아야 비교가 선다
3. 세 추정기 값이 2프레임 이내로 붙으면 **음향값(스펙트럼)을 택한다.** whisper 는 검산용이다
   (00006 실측: whisper-medium 만 믿었으면 F21 「십팔」이 **12프레임 늦었다** — 1.558 은 「팔」 음절이었다.
    반대로 F02 「이십구만」에서는 whisper 가 묵음 구간 안(0.760)으로 **이른** 쪽으로 틀렸다)

### 🔴 컷머리 어절은 **체계적으로 +0.13초 이르다** — 원인이 밝혀졌다 (2026-09-10 · W1)

00006 실측: F02·F22 가 **정확히 +0.130 초**씩 이르다. W7 도 F16·F19·F20 에서 +0.125 / +0.205 / +0.125 를 쟀다.

**원인**: 컷머리 어절이 **앞 구절의 감쇠 꼬리**(−20dB → −55dB, 약 0.12초)를 자기 시작으로 잡는다.
whisper 가 프레임 경계에서 첫 어절을 0 으로 클램프하는 것과 겹쳐 두 배로 이르다.

**지금의 대처**: 컷머리 어절에 착지시킬 때는 **반드시 wav 를 직접 재라.**
「직전 골 이후 **첫 유성 개시**」가 온셋이다 — 골 바닥도, 감쇠 꼬리의 시작도 아니다.

**근본 수정 후보** (아직 안 했다): `pipeline/transcribe.py` 또는 `hf-audio.mjs` 에서
**컷머리 어절에 한해** silencedetect 로 첫 비무음 지점을 찾아 앞당겨진 시작을 그리로 스냅.
⚠️ 이미 워커가 측정을 마친 프로젝트에서는 **재생성하지 마라** — 동결된 프레임의 근거가 무효가 된다.

### 🔴 `snapshot --zoom` 은 **동결 중에도 쓸 수 있다** (2026-09-10 · W3)

`hyperframes snapshot` 은 **정지 캡처**다 — 렌더도 프리뷰 서버도 아니다.
동결 규약이 막는 건 **쓰기**지 보기가 아니다. 고치는 중에도, 동결한 뒤에도 확인할 수 있다.

```bash
node pipeline/hf-cli.mjs <p> snapshot --at 9.14,9.30 --no-end --zoom "60,470,560,190" --zoom-scale 3 -o chk
#   --zoom "x,y,w,h" 은 고밀도 크롭(deviceScaleFactor 상향)이라 레이아웃이 안 바뀐다
#   --describe 는 외부 전송이므로 끈다
```

**00006 실측**: 워커가 로고 겹침을 고치다 **두 제목 줄을 38.6px 겹치게 만들었고**,
그걸 그 자리에서 잡아 준 게 이 명령 하나뿐이었다. 소스 계산으로는 안 보였다.

🔴 **자기가 고친 자리는 반드시 확대해서 봐라.** 수정이 새 결함을 만드는 일이 실제로 일어난다.

🔴 **`-o` 를 반드시 붙여라 — 프로젝트 `snapshots/` 는 공용이다** (2026-09-11 · 00009 · pitfalls §65).
파일명이 `frame-NN-at-<초>s.png` 라 **찍은 사람을 구분하지 않는다.** 워커 여럿이 동시에 찍으면
서로 덮어쓰는데 **에러가 안 난다** — 파일은 멀쩡히 있고 열리기까지 한다. 그래서
「내 프레임을 확인했다」는 보고의 근거가 **남의 프레임**일 수 있다.

```bash
... -o <세션 스크래치패드>/w-<내 이름>     # 팀리드가 경로를 줬으면 그것을 쓴다
```
⚠️ `-o` 없이 찍었다면 **파일 mtime 과 내 명령 실행 시각을 대조**해라. 어긋나면 남의 것이다.

### 🔴 동결 확인에 답할 때 — **다시 재고 답해라** (2026-09-10 · 00006)

팀리드가 「지금 `<md5>` 로 굽는다, 맞나?」를 물으면 **예/아니오로만** 답하되,
**답하기 직전에 `md5` 를 다시 잰다.**

> **「예」는 *내 보고서와 같다*가 아니라 *방금 잰 값이 팀리드가 말한 값과 같다*는 뜻이다.**

00006 에서 팀리드가 워커 동결본(자막 한 줄·CSS 두 줄)을 통지 없이 고친 뒤
**워커 보고서의 옛 md5 를 그대로 인용해** 동결을 선언했다. 두 번 다 워커가 **다시 재서** 잡았다.

⚠️ 대칭 실패도 있었다 — 워커가 두 시간 전에 읽은 CSS 값을 **기억에서 꺼내**
「아직 안 고쳐졌다」고 보고했는데 파일에는 이미 반영돼 있었다.
**바이트를 말할 거면 바이트를 읽어라.** 기억은 근거가 아니다.
