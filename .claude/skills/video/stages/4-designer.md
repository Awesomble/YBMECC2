# ④ 그림과 모션

**🔴 순서 — 첫 3초가 먼저다 (공용 SKILL 맨 앞 「최우선」).** 정지 시안은 0.0초 포스터(주제 제목·후킹·키 비주얼)부터 가장 공들여 만든다 → B 보고(올리고 같은 턴에 계속) → **훅 잠금**(아래 「안무」의 첫 절: cut-01을 최종 자산·자막·효과음까지 안무하고 `hook-check` 시트로 합격시킨다) → 대표 본문 → 본문 팬아웃 → 조립·소리 → C(시트 0 = 훅 시트). 이 단계에서 가장 많은 시간과 시도를 쓰는 곳이 훅이며, 네 행의 합격 조건을 모두 충족하면 멈춘다. 0초 포스터를 정지 상태로 둔 채 완성으로 처리하지 않는다 — 포스터는 0~1초에 움직인다. 모션 자율성은 공용 SKILL 기술 계약을 따른다.
읽을 것은 채널05 §2·§3-1, `docs/09-safezone.md` §1, `docs/02-pitfalls.md` 색인의 관련 항목(최소 §112·§113), `docs/14-hyperframes.md`·`docs/11-motion.md`의 필요한 절이다. `docs/12-brand.md`는 기술 참고가 필요할 때만 연다. ABMEN의 색·폰트·락업은 채널 문서와 공용 SKILL 기술 계약 표가 우선한다.
메인이 직접 프레임을 쓰면 `pipeline/templates/worker-brief.md` ⑤-0의 위험 구간 배치 검산을 적용하고, 워커에게 맡기면 공통 계약과 해당 절을, ③에서 확정한 시간축·장면 간 공통 시각 체계(제목·키커·라벨 처리)와 함께 첫 패킷에 전달한다. HyperFrames는 공용 SKILL 「실행 환경」의 읽기 범위를 따른다.

## 골격과 정지 화면

**채널05 §3-1을 이번 제작의 품질 계약으로 적용한다.** 정지 화면은 1편처럼 주연·결론·조건의 순서가 명확해야 하고, 안무는 2편처럼 그 주연의 행동이 설명을 진전시켜야 한다. 승인 시안의 색·구도만 복제해 모든 장면을 같은 정보판으로 만들지 않는다. 소재가 달라지면 그 소재의 수량·작동·선택 관계로 새로 설계한다.

1. projects/<p>/hyperframes/를 확인한다. new.sh로 이미 만들어졌으면 재사용한다. 비어 있는 기존 프로젝트만 `node pipeline/hf-project.mjs <p> init`으로 초기화한다. 프로젝트 안에서 npx를 실행하지 않는다.
2. 브랜드 폰트·락업 자산·paused 루트 타임라인·window.__timelines 등록을 갖춘다.
3. ③의 타이밍·자산과 README의 **디자인 방향·에셋 제작 경로·생성 요청**을 받아 중심 오브젝트·시선 순서·정보 위계를 구현한다. 확정된 풀화면 그래픽 한 계열(채널05 §2 — 사진풍·3D·코드·셰이더 층이 같은 계열 안의 재료다) 안에서 1080×1920 배경과 큰 사물을 구성한다(옛 크림 무대·큰 락업을 시각 기준으로 복구하지 않는다). 템플릿 개정(2026-09-21·09-25) 전에 만든 기존 프로젝트를 이어 작업하면 설치된 팔레트·폰트·락업이 채널05 §2·§4와 맞는지 먼저 대조한다(락업은 `root-lockup.mjs`). docs/channel/05-brand-pipeline.md를 따르고, 받은 이미지를 직접 열어 구도·재질·해상도·합성 상태를 확인한다. **3D는 필요한 사물·건물 요소부터 만들고 표면이 중요한 부분은 사진/이미지 매핑까지 완성한다.** 실재 건물·구조물은 docs/16 §4-1의 실물 형상 대조(실물 사진과 같은 시점 스틸 → `ref-photos --sheet`)를 통과한 뒤에 동작·본 렌더로 간다. docs/16-blender.md §4·§5-1·§5-2의 요소 시안·매핑/카메라 검수·최적화를 거쳐 알파 영상을 root에 합성한다. 배경의 빛·색면이나 생성 사진의 표면(빛샘·굴절·물결·결)을 움직이는 데는 셰이더 층도 고른다 — `node pipeline/shader-fx.mjs list`에서 고르고, 메인이 `node pipeline/shader-fx.mjs <p> install`을 한 번 돌린 뒤 프레임은 풀프레임 캔버스 하나와 `ABMShaders.mount`만 쓴다(작성 계약 `docs/14-hyperframes.md` §16). 쓰기로 한 장면·효과·이유는 README 에셋 경로에 한 줄로 남긴다. 브랜드(팔레트·서체·로고)는 고정이고 **주연 표현·카메라·빛 층·이징 성격은 README 「디자인 방향」에 이 소재의 값으로 정한 것을 쓴다** — 편마다 새로 고르되, 테마·레퍼런스 검색을 처음부터 반복하지는 않는다.
   참고 화면을 썼다면 그 사이트의 레이아웃 전체나 `DESIGN.md` 수치를 옮기지 않는다. 캡처에서 확인한 피사체·타이포·여백 관계를 1080×1920의 첫 상태에 맞추고, 실제 발화에 맞는 주연의 변화·결과·다음 장면 연결로 구현한다. 참고 설명과 화면이 다르면 화면을 기준으로 판단한다.
4. **충돌 위험이 있는 정보부터 배치 검산한다.** 가격·단위·제목과 가까이 지나는 소재의 x·y·w·h·동시 정착 구간을 worker-brief ⑤-0 방식으로 확인한다. 모든 장식을 표에 채우거나 표의 편의를 위해 장면을 같은 카드 구도로 만들지 않는다. 의도한 겹침은 유지하고 실제 정보 가림을 고친다.
5. hyperframes/STORYBOARD.md를 실제 구현 설계도로 사용한다. 프레임·실측 길이·focal·roles·시작→결과 상태·전환·사용 자산을 적고 기존 형식을 유지한다. 디자인 방향 설명은 README를 참조하고 복제하지 않는다.
6. **0초 포스터는 이 단계 전에 아래 「0초 포스터 — 디자이너 절차」로 만든다**(3안 → 비교 시트 → 고른 안을 cut-01 0초에 구현). 대본과 **실제 정지 화면 시트**를 B 보고로 올리고 같은 턴에 훅 잠금을 시작한다. 시트 맨 앞에 `output/review/poster-sheet.png`(고른 안 크게·나머지 작게)와 고른 이유 한 줄, 실제 root의 0.0초 화면(`node pipeline/hf-cli.mjs <p> snapshot --at 0 --no-end -o ../output/stills/frame0`)과 README 「첫 3초 비트」·0초 포스터 세 줄을 놓고, 폭 360px과 시트의 그리드 칸에서 「최우선」 0.0초 포스터 행과 원칙 1·2·3·5로 판정한다. 한 줄씩 본다:
   - 주제가 읽히고 **볼 이유(후킹)가 가장 큰 글자로** 바로 읽히는지.
   - 키 비주얼의 주인공이 작은 칸에서도 무엇인지 보이고 반전이 그림 안에 있는지.
   - 0초 글이 제목·후킹 두 덩어리뿐인지.
   - 빈 곳이 주제 재료로 채워졌는지, 다음 행동의 단서가 화면 안에 보이는지.

   하나라도 빠지면 B에 내지 않고 고친다. 0~3초 움직임은 B 뒤 훅 잠금에서 본다. 조건의 작은 글씨가 중심을 빼앗으면 본문으로 옮기되 사실을 오해시키지 않는다. 다른 그림 도구의 포스터는 스타일 참고로 표시한다. 시안 승인은 첫 3초의 동작 검증을 대신하지 않으며, 본문의 구도·세부 정보 전개를 동결하지 않는다.

폰트·CI·제품은 로컬 자산으로 로딩하고, 경로는 HyperFrames 프로젝트의 assets/ 상대 경로를 사용한다.
공유 자산을 이동하지 말고 복사한다. 장식용 글리프가 깨지면 적절한 SVG 아이콘을 사용한다.
시안은 실제 출력 비율을 유지한 휴대폰 표시 크기에서도 본다. 주연의 실루엣·크기 대비와 읽는 순서가 약하면 **구도·타이포·자산을 먼저 수정**한다. 제목+카드가 반복되는 이유가 없으면 구조를 바꾸고, 의미 없는 박스·중복 문구·작은 장식을 덜어낸다. 의도된 비교·반복은 유지한다. 최종 그림이 필요한 슬롯은 임시 상태로 표시한다.
**인물·동물·주연 오브젝트를 새로 그리거나 자세를 바꾸면** 실제 root 캡처를 폭 360px로 줄인 전체 화면과 그 부분 크롭으로 실루엣을 판정한다. 같은 색 부품(얼굴·목도리·손)이 맞닿아 혹이나 다른 신체로 읽히면 부품을 빼거나 색을 나눈다. 1080 확대 캡처만으로 통과시키지 않는다(pitfalls §113, 00006: 사용자 지적 후 렌더 2회 추가).
시트는 보고 직전에 한 번 만든다. 문구·시간을 고친 뒤에는 바뀐 칸만 다시 확인한다. `hf-cli snapshot -o`의 상대 경로는 hyperframes 폴더 기준이므로 `-o ../output/stills`처럼 준다.

시안에서 생성 이미지가 훅·핵심 장면의 품질을 더 높이겠다고 판단하면 ②의 형식으로 README에 그 에셋을 추가하고 `asset-prompts --generate --only=<id>`로 바로 만든다. 작업자가 직접 그릴 수 있다는 이유로 이 선택을 생략하지 않는다.
생성 중인 에셋은 표시된 임시 배치로 구도만 준비하고, 다른 장면·코드·모션은 계속 만든다. 최종 이미지 없이 임시 도형을 완성본으로 납품하지 않는다.
생성 결과에 문제가 있으면 ②의 **편집 형식**(`Edit`·`Keep unchanged`, 참조 첨부=원본 id)으로 한 가지씩 고치는 에셋을 추가해 생성하거나, 프롬프트를 고쳐 `--only=<id> --force`로 다시 만든다. 통과한 에셋은 다시 만들지 않는다. 크기·차이는 README 「에셋 생성 요청」 끝의 `### 수령 검수`에 적는다.
실재 대상의 생성 이미지는 ② 「실물 대조」의 대조 시트(`ref-photos --sheet`)와 식별 특징 n/N을 거친다 — 시트가 없으면 `--accept`가 거부한다. 생성 이미지는 필요한 레이어·마스크·오브젝트 또는 3D 표면 텍스처로 연결한다. 매핑용은 대상 면·UV·최대 회전·카메라 근접에서 직접 확인하고, 단색 블록아웃을 표면 완성본으로 대신하지 않는다. 숫자·자막·비교 관계·타이밍은 코드로 제어한다.
`node pipeline/asset-prompts.mjs <p> --check`는 assets 장부·경로·크기·승인 지문을 검사한다. 배경에 컷아웃 기준을 적용하지 않는다. 실제 생성 파일을 열어 알파·잘린 부위·왜곡·시리즈 일관성을 보고 HF 경로로 복사한 뒤 `node pipeline/asset-prompts.mjs <p> --accept=calendar-paper --confirm-visual`로 승인 지문을 기록한다. 최종 `--check --final`은 미생성/미승인·파일 변경·렌더 참조 누락을 막는다. 시각 품질은 직접 본다.

hf-compile.mjs는 필요하면 골격·시안용으로 사용한다. 이미 직접 그린 최종 프레임을 재컴파일로 덮지 않는다.
최종 프레임은 compositions/frames/에서 직접 HTML·GSAP·SVG 등으로 구현한다.
영상별 값은 프로젝트 안에 두고 pipeline/motion/src/ 공용 엔진을 바꾸지 않는다.

1. **서로 다른 3안을 만든다.** README 0초 포스터 세 줄과 실물 대조를 통과한 키 비주얼(사진·컷아웃·3D 알파)로 세션 스크래치에 1080×1920 정적 HTML 세 장을 쓴다. 세 안은 제목 위치의 변주가 아니라 **볼 이유를 보이는 서로 다른 아이디어**다.

   - **③ 글자 주도:** 후킹 구절이 주인공이고 그림이 받친다. 장면 속 간판·표지판이 글자가 되는 구성도 여기 든다.
   - **④ 본문 최고 장면(세 안 중 하나는 반드시):** STORYBOARD·프레임 중 가장 후킹이 센 장면의 정점 상태를 그대로 0초로 가져와 제목·후킹만 얹은 안. 포스터는 영상에서 가장 센 장면이어야 한다 — 본문의 어느 장면보다 약한 포스터는 반려(2026-10-21 사용자 「영상 구성 장면 중 가장 후킹 있는 디자인부터 시작」).
   
   시안에 셰이더 배경·사진 효과를 쓰면 `<head>`에 `pipeline/templates/hyperframes/shaders-core.js`·`abm-shaders.js`를 절대 경로로 싣고 `ABMShaders.mount`를 그대로 쓴다(이미지·폰트도 `file://`가 아닌 절대 경로) — 3번의 `poster-sheet`가 그 안만 WebGPU로 찍는다(`shader-fx shot`). 색·크기·한 단어 같은 미세 조정은 한 안을 고른 뒤에 한다. 세 안 모두 로고(x80·y228·h112)·정보 정착(x60~960·y360~1360)·자막 구역(y1372~1540)을 지킨다.
2. **디자이너 기본기로 짠다.**
   - **위계:** 가장 큰 글자는 후킹, 곧 볼 이유다. 주제 제목은 대상·장소 이름을 **Hahmlet 900**(`class="abmen-poster-title"` — 행간 0.86~0.9, 자간 -0.03~-0.035em)으로 쓴다. 후킹이 그 이름을 품으면 구절 전체를 Hahmlet 한 덩어리로 써도 된다. 이름만으로 볼 이유가 되는 명소(JEJU)는 이름을 크게 쓰고 후킹을 바로 곁에 둔다. 따로 쓴 후킹 값·숫자·자막·라벨은 Inter다. 밝은 바탕엔 Navy, 어두운 바탕엔 Cream.
   - **크기:** 0초에 보이는 가장 작은 글자(보통 제목)도 1080 기준 **110px 이상**(폰 폭 390pt에서 약 40pt — 프로필 그리드 칸에서도 읽힌다), 후킹은 제목보다 크다. 제목이 길어 110px로 두 줄을 넘으면 약칭을 쓰거나 후킹이 이름을 품게 한다(2026-10-21 사용자 「제일 작은 폰트를 더 크게」 · `stage-gate 4`·`hook-check`가 소스의 font-size를 잰다 — 그 전 9편 제목은 62~106px였다).
   - **0초 글은 제목·후킹 두 덩어리**(와 로고)뿐이다. 보조 설명 문장·두 번째 값·칩은 본문으로 옮긴다. 강조색은 한 곳에만 쓰고, 후킹의 강조와 키 비주얼 위 표시를 같은 색으로 잇는다.
   - 대담함은 한 곳에만 쓴다. 다 만들면 장식 하나를 뺀다.
   - **뻔한 기본값으로 반려되는 것:** 작은 칩·알약 라벨로만 주제를 알림, 분류명 제목이 가장 크고 볼 이유는 작은 둘째 줄, 제목 자리를 비우려고 멀리 잡아 작아진 주연, `A · B` 가운뎃점 라벨, 원형 인셋, 큰 숫자 + 작은 라벨뿐인 정보판, 가운데 띄운 카드, 사진 위 반투명 카드, 여러 곳에 흩어진 강조색. 00051 납품본 0초(칩 라벨·원형 인셋·`118F · GLASS FLOOR`)가 이 목록의 예다.
3. **비교하고 비평한다.** `node pipeline/poster-sheet.mjs <p> <고른 안.html> <안2.html> <안3.html> [--before <지금 0초 png>] [--body <본문 최고 장면 png>]` → `output/review/poster-sheet.png`. 위 칸은 폭 540·270px, 맨 아래 줄은 인스타·틱톡 프로필 그리드 크기의 3:4 칸이다. `--body`에는 본문에서 가장 후킹이 센 장면의 정점 스틸(`node pipeline/hf-cli.mjs <p> snapshot --at <정점 초> --no-end -o ../output/stills/peak`)을 넣는다. 이렇게 판정한다:
   - 그리드 칸에서도 주인공이 무엇인지, 후킹 구절이 무엇인지 보이나.
   - 볼 이유(남겨 둔 공백)를 한 줄로 말할 수 있나.
   - 위 반려 목록에 걸리나, 장식 하나를 뺄 수 있나.
   - 맨 끝 칸(본문 최고 장면)보다 포스터가 약하지 않나 — 약하면 그 장면의 디자인에서 다시 시작한다. 가장 작은 글자가 그리드 칸에서도 읽히나(110px 이상).
   
   고쳐서 다시 뽑는다(00051 시험: 타워를 따라 내려가던 지시선을 빼고, 제목 뒤 타워가 단어 끝 글자만 가리게 옮겼다).
4. **고른 안을 cut-01 0초에 구현한다.** 포스터 글자는 마크업에 둔다(stage-gate ④가 제목·후킹 글자와 서체를 본다). 첫 자막은 첫 어절 시각부터 띄워, 0초 한 장에는 자막이 없게 한다(`hook-check`가 본다). 0~1초에 주연이 움직일 여유를 남긴다. 고른 안과 이유는 STORYBOARD 첫 행에 한 줄로 적는다.

### 모든 컷의 안무

승인된 시각 방향 안에서 **발화가 요구하는 변화와 그 결과**를 먼저 정한다. 주연 사진·그래픽이 실제로 변하고, 읽을 결과가 남아야 한다. 정적인 정보판+작은 강조만으로 연출을 완료하지 않는다.

1. 컷마다 비교·증감·분해·이동·반전·증거 제시 등 발화의 역할을 잡고, 주연의 **시작 상태 → 동작 정점 → 읽을 결과 → 다음 장면의 연결**(동작은 `[대상]+[동작 이름]+[방향·경로]+[실측 어절 시각]` — 형용사만 쓰지 않는다, `docs/11-motion.md` 「동작은 이름·방향·시각으로」)과 채널05 §3-1의 **핵심 발화·자막 강조·화면/전환·보조 그래픽·소리 동기화 지점·읽을 정착**을 같은 STORYBOARD 행에 적는다. 통계·가격·전후 비교라면 축과 기준, 원본 상태를 바꿔 의미를 왜곡하지 않는다.
2. 그 물리를 `resources/motion/`과 `node pipeline/motion-signature.mjs menu <p>`에서 찾는다. 빛·색면·사진 표면의 변화는 `node pipeline/shader-fx.mjs list`(움직임·×2 표시)에서 찾고 `at(t)`로 발화 정점에 맞춘다. 맞는 것이 없거나 더 나은 사건이 필요할 때만 외부 레시피의 **의도·동작 단계·실패 사례**를 좁혀 확인한다. 즐겨찾기 카드 수나 미사용 효과 종류를 목표로 삼지 않는다.
3. 외부에서 고른 동작은 이 영상의 소재·세로 화면·실측 발화·HyperFrames/GSAP에 맞게 다시 구현한다. 예시 프레임 수·이징·카메라 배율·색·테마를 그대로 이식하지 않는다. 실제로 사용한 참고(URL/카드 이름·빌린 원리·바꾼 점)는 STORYBOARD 「서명 동작」 줄 뒤에 짧게 적는다(②가 둔 줄 — `motion-signature check`가 읽는다). 코드·이미지·음원을 가져오면 각각의 라이선스도 확인한다.

모션 원리가 막힌 장면은 먼저 `resources/motion/`을 보고, 필요한 촬영·전환 개념만 [Eyecandy](https://eyecannndy.com/)에서 찾아 주연의 전후 상태로 번안한다. Eyecandy는 원본 영상의 재사용 권한을 주지 않으므로 화면을 다운로드해 영상에 넣지 않는다. 값·라벨·아이콘이 **제자리에서 다른 상태로 바뀌는** 원리는 [transitions.dev](https://transitions.dev/)에서 빌린다 — 바뀐 부분만 교체(Number pop-in `data-same`·Text morph), 주연이 튀면 이웃이 거리만큼 약하게 따라옴(Avatar group hover), 확인 표시의 페이드·회전·흐림·선 그리기 겹치기(Success check). 거기 값은 앱 UI용(이동 4~30px·배율 0.96~0.99·0.5초 이하·CSS 클래스 토글이라 seek 비결정)이니 원리만 가져와 GSAP 타임라인에 휴대폰 크기로 다시 짓고, 숫자 롤러(Spinning counter)는 쓰지 않는다. 스킬·CLI는 설치하지 않는다(일반 「animate」 요청을 가로챈다). 외부 레시피는 이름이나 인기보다 실제 발화·소재에 맞는지 대표 구간에서 검증한다. 다른 도구·사례는 필요할 때 `docs/13-astra-agent-motion.md`에서 찾는다.

- 글자를 읽는 구간과 움직임이 일어나는 구간을 함께 설계한다. 움직이는 중간 프레임만으로 정착 레이아웃을 판정하지 않는다.
- 무대 안의 거리·속도·배율·효과·의도적 겹침과 **무대 밖을 넘나드는 시그니처 모션**은 자유다. root 전체 캔버스 클리핑과 개별 소재의 의도된 마스크를 구분한다. 무대 y360~1360 래퍼 전체에 overflow:hidden/clip-path를 기본으로 씌우지 않는다. 실제 정보·락업·자막 가림과 누락을 수정한다.
- 어떤 시각으로 seek해도 같은 결과가 나와야 한다. 실시간 시계·미고정 난수·자동 재생에 의존하지 않는다.
- 숫자는 말한 값만 보인다 — 값 단어 실측 시각에 최종값으로 꽂고(`resources/motion/` M4), 0에서 세거나 중간값을 굴리지 않는다(00043·00072 반려). 값이 바뀌는 컷(1,299→1,305·$5→$50)은 두 값이 공유하는 앞자리·단위를 붙박고 **바뀐 자리만 한 박자에 교체**한다(흐림·이동 교차). 라벨·단위가 같이 바뀌면 같은 박자에 묶는다. 워커 패킷에 이 줄을 그대로 넣는다.

**대표 구간(훅과 본문 핵심 설명·인접 연결)은 실제 root에서 최종 자산·자막 강조·선택한 소리를 합쳐** 휴대폰 크기로 상태 변화·읽는 순서·소재 완성도를 확인한다(채널05 §3-1). 임시 도형으로 동작만 통과시킨 뒤 완성 자산의 질감·실루엣·매핑 검수를 뒤로 미루지 않는다. 다른 구간의 모션 시안은 `node pipeline/motion-preview.mjs <p> --start=<초> --end=<초>`(브라우저 허용 환경)로 만든다. motion-preview는 snapshot 시퀀스+나레이션 참고본이며 BGM·SFX·60fps·최종 합성 검증을 대신하지 않는다.

개선은 기존판과 수정판의 **같은 내용·발화 구간·표시 크기**로 대조하고, 무엇이 더 잘 읽히거나 설명되는지 실제 시각을 짚는다. 작은 흔들기·색 교체·트윈 증가만으로 개선을 선언하지 않는다. 소스만 고쳤으면 시각 개선은 미검증이다. 대표 구간이 약하면 나머지 장면을 같은 방식으로 확장하기 전에 고친다. 새 승인·전편 변형본은 만들지 않는다.
타이밍·오디오·공용 index의 소유권을 유지하고 프레임 담당자가 임의로 바꾸지 않게 한다.

`motion-preview.mjs`는 같은 `output/review/motion-preview.mp4`와 `.json`을 덮어쓰므로, 계속 쓸 구간은 두 파일을 함께 구간 이름으로 옮긴 뒤 다음 구간을 만든다(`hook-check`는 0~3초를 `motion-preview-hook-0-3.*`로 스스로 옮긴다). stage-gate 4는 0~3초 재생 기록과 훅 잠금 시트(`hook-check.json`)가 현재 소스·나레이션 지문과 같은지 대조해 없거나 낡으면 경고하고, 2026-10-04 이후 골격(`lib/hook.mjs` BEAT_SINCE)에서 「첫 3초 비트」가 비어 있으면 하드로 막는다. 본문을 고쳐도 지문이 바뀌므로 C 직전에 `hook-check`를 다시 돌린다(소스가 같으면 재사용). 지문을 고치거나 최신성 게이트를 우회하지 않는다. 사본·백업은 늘리지 않는다.

**정착 시트 외에 검사할 시각을 STORYBOARD에 적는다.** 핵심 자막의 등장·확대/강조 정점·읽을 정착을 실제 프레임에서 확인한다. 글자가 가장 커지거나 회전·이동하는 순간에도 가림·잘림·안전영역을 검사하고 문구·발화 타이밍·SRT 대응을 유지한다. 숫자·통화·중량/수량·개당/묶음 설명이 바뀌는 전/중/후, 소재가 글자 근처를 지나는 시각, 전환의 가림 정점·진입·퇴장, 마지막 판단 화면을 실제 root에서 확인한다. 가격은 새 값인데 라벨은 이전 단위인 중간 상태를 남기지 않는다. 물체끼리의 의도된 겹침은 유지하되 읽어야 할 글자가 가려지면 경로·레이어·시간을 고친다. 기존 자동 검사의 고정 표본과 바운딩 박스가 이 확인을 대신하지 않는다.

### 인스타 CTA 판

cuts.json `ig_cta`가 있는 편(지도 핀 자동 · 요청한 링크 편 — 공용 SKILL 「인스타 CTA 판」)도 프레임은 다른 편과 같다 — CTA 화면을 그리지 않는다. 납품 뒤 `ig-cta`가 3초~끝 자막 아래(x120~900·y1584~1654)에 스티커(버건디 알약·Gold 말풍선·Gold 키워드 칩·DM 봉투)를 얹으므로, 그 띠는 원래대로 읽을 글자·주연을 정착시키지 않는 플랫폼 UI 인접 영역으로 둔다(배경·장식은 그대로). 🔴 엔딩 카드의 법정 표시(상호·등록번호·교습과정)도 이 띠 밖(위)에 둔다 — 인스타 판에서 스티커가 덮는다.

## 조립과 소리

```bash
node pipeline/hf-audio.mjs <p>
node pipeline/hf-project.mjs <p> sync
```

좌상단 로고는 공용 SKILL 기술 계약 표의 규격이다(x80·y228·높이 112). 새 골격(`new.sh`)이 넣고, 옛 골격으로 시작한 편은 조립 뒤 `node pipeline/root-lockup.mjs <p>`로 적용한다(`--sub`는 호환 옵션). 0초 구도와 무대 상단 헤드라인·태그는 로고 상자(x80~237·y228~340)를 피해 잡는다. 실제 캡처에서 위치·크기·배경 대비(크림·라임 배경 포함)를 확인한다.

hf-project sync는 새 관리 골격의 슬롯·오디오·총 길이를 시간 정본에서 갱신한다. 기존 수동 index는 관리 마커가 없으면 보존하고 중단하므로, 그 프로젝트의 master/캡션/안무를 직접 맞춘다. sync는 프레임 내부 GSAP·자막을 재작성하지 않는다.
index.html에는 say 유무와 무관하게 **컷마다 audio를 하나씩** 배치한다.
**본문 전체 확장 전(훅 잠금 1번), 실제 root에서 자막 추출까지 확인한다.** 슬롯·총 길이·기존 음성 실측을 맞춘 뒤 아래 지원 계약 중 해당 프로젝트의 한 경로를 사용한다. 검사용 유료 음성을 추가 생성하지 않는다.

- 프레임 자막: 마운트된 프레임 안의 정확한 `class="clip caption"`과 프레임 로컬 `data-start`·`data-duration`·실제 문구.
- 루트 자막: root의 `class="clip"` 슬롯에 `data-composition-id="captions"`·`data-composition-src="compositions/captions.html"`·유효한 시작/길이를 지정한다. 해당 파일에도 `data-composition-id="captions"` 루트와 `class="clip cap"` 자막 클립의 시작/길이·실제 문구가 있어야 한다. 자막 시각은 마운트 시작에 대한 로컬 초다.
- 자주 난 함정: 프레임 안 클래스·id에 자막 이름(`cap`·`caption`)을 쓰지 않는다(layout-scan이 자막으로 잰다). flex 자막 상자에서는 문구를 블록 줄 요소로 감싸야 강조 span 앞뒤 공백이 사라지지 않는다. 인라인 transform 확대는 앞뒤 단어의 자리를 밀어주지 않아 겹칠 수 있다. 확대 여백·래퍼·레이어를 확보해 정점에서 확인하거나 색·굵기·줄 단위 강조를 선택한다. 단어 확대 자체를 금지하지 않는다.

`node pipeline/hf-export.mjs <p>`로 현재 구현한 발화의 자막 청크가 빠짐없이 추출되는지 확인하고, SRT 문구·시간을 실제 화면·음성과 대조한다. root에 직접 놓아 눈에 보이는 일반 자막 div만으로는 추출 계약을 충족하지 않는다. 임시 더미 자막이나 과거 추출물로 통과시키지 않는다. 초기 구조 확인 후 최종 전체 자막 검수도 유지하며, 자막 구역을 지켜 렌더와 SRT가 일치하게 한다.
장면 전환의 배경·겹치는 시간·레이어 순서를 확인한다.

BGM은 README 「디자인 방향」의 **BGM 정서** 줄(②에서 정함)대로 `resources/music/cc0/`에서 고른다(`CREDITS.md` 「정서」 열) — 맞는 칸이 비면 `resources/music/README.md` 「새 곡 받을 때」로 먼저 들인다. 밝은 곡을 기본값으로 깔지 않는다(2026-10-21 감사). 유효한 구간을 자르고 음성과 섞으며, audio_meta.json에 title·composer·source·license·**mood·why**를, STORYBOARD의 music에 원곡 파일명·시작초·정서를 적는다. 같은 곡은 정서가 맞고 이유를 적었을 때만 — `stage-gate 4`가 직전 5편과 대조한다. 시작초·대역 처리는 곡마다 잰다. 절차·형식·레벨은 docs/14-hyperframes.md §5.
**기획한 효과음을 실제 root에 조립한다.** [효과음 운영](../../../../resources/sfx/README.md)의 **④ 준비·동기화·조립 / ④·⑤ 청취**를 적용해 `audio_meta.json.sfx`를 한 번에 맞춘다. 화면 상황별 큐를 `event`(화면 사건 표시 초)로 모두 넣고 `node pipeline/sfx-fit.mjs <p> --apply`로 파일 안 동기점만큼 앞당긴 `at`을 채운 뒤, `node pipeline/sfx-fit.mjs <p>` 안내(재질 불일치·대사 위 음성 대역)를 한 번에 반영하고 `node pipeline/sfx-level.mjs <p>`로 대사 대비 크기를 목표(0dB 부근)에 맞추고(일부러 작게 둘 큐는 `"subtle": "<이유>"` — 효과음 운영) 묻힘 0을 확인한 다음 렌더한다. 대표 구간에서 대사·BGM과 함께 확인한다. 소리 선택과 재생 시작초의 정본을 프레임마다 복제하지 않는다. 효과음 라이선스 등급은 verified만 새 편에 허용한다(00002번부터 unverified는 조립 실패 — YBMECC 이식 시행 번호 — `node pipeline/sfx-fit.mjs --catalog`, `--find`의 ⛔).

## 검증과 C 보고

전체 브라우저 검사 전에 관련 수정사항을 모아 반영하고, 초기 상태·JS 문법·선택자·자산 경로·가격/단위의 동시 교체를 먼저 확인한다. 특히 정확히 0초의 숨김 상태는 CSS/마크업 또는 즉시 적용되는 초기화로 명시한다. paused timeline의 0초 `set`에만 의존하지 않는다. 소스를 동결한 뒤 전체 스캔·번호 시트를 만들고 단계 게이트를 실행한다. 이후 수정은 공용 SKILL의 영향 범위 원칙에 따라 재검수하며, 필수 게이트가 최신 결과를 요구하면 충족한다. 명령을 줄이려고 실패·지문·시각을 조작하지 않는다.

`node pipeline/hf-cli.mjs <p> lint`로 고정 CLI의 lint를 실행한다. 브라우저 검사가 가능한 환경에서만 다음을 실행한다.

```bash
node pipeline/layout-scan.mjs <p>
node pipeline/review-sheet.mjs <p>
node pipeline/stage-gate.mjs <p> 4
```

현재 샌드박스에서 브라우저 실행이 불가하면 `node pipeline/layout-scan.mjs <p> --static` 등 정적 검사를 마치고 실제 스캔·시트는 실행 가능한 환경에 넘긴다.
정적 검사나 오래된 시트를 최신 눈검사로 보고하지 않는다.

번호 시트 전체를 직접 보고 훅·절정·조건·마무리의 위계, 잘림·가림·폰트·CI·자막을 확인한다.
동작·이음매는 전후 프레임과 재생으로 본다. 타이밍은 소스·음성 실측으로 확인한다. 3D 영상 레이어와 셰이더 캔버스는 layout-scan이 보지 못하므로(pitfalls §119 · docs/14 §16) 라벨 정착·카메라 근접·2D↔3D 전환과 셰이더 위 글자의 대비·가림(`at()` 정점과 정착 시각)을 `snapshot --at`으로 보고, 사진 매핑의 늘어짐·투영 미끄러짐·이음선·뒷면·알파 테두리·깜빡임도 실제 동작에서 확인한다(docs/16 §4). 실재 구조물은 실물 형상 대조 시트가 현재 3D 소스 기준인지 stage-gate 4가 본다.
**렌더 전에** `pipeline/still-scan.sh <p>`와 각 장면 시작 0.1초 캡처로 같은 구도의 장시간 유지와 장면 진입 공백(페이드로 첫 프레임이 비는 것)을 확인하고, 긴 설명 구간은 조밀 캡처나 motion-preview로 주연·카메라가 실제로 움직이는지 본다. 이 유형은 렌더 뒤 render-gate에서 드러나면 렌더 1회를 더 쓴다(00006 v1).
**C 제출 전 ⑤의 「렌더 전 검토」를 적용한다.** 화면 오류뿐 아니라 훅→본문→결말의 약속, 반복 배치로 묻힌 관계, 인접 장면의 소재 완성도를 검토한다. 수정사항을 fix-batch로 모아 처리하고 최신 시트를 C 보고로 올린 뒤 같은 턴에 ⑤ 렌더로 간다. C 시트의 맨 앞(시트 0)에는 `hook-check`를 다시 돌린 최신 `hook-sheet.png`와 대조 출력을 둔다.

**스튜디오는 사용자가 요청할 때만** `pipeline/preview.sh <p> user`로 연다.
자체 확인이나 렌더 전이라는 이유만으로 열지 않으며, 사용자가 보고 있는 세션을 임의로 껐다 켜지 않는다. 셰이더 층이 있으면 「재생 중 셰이더가 멈춰 보일 수 있다(미검증) — 판정은 렌더본」이라고 함께 알린다.
⑤에 소스·시트·게이트 결과·남은 미검증 항목을 넘기고 같은 턴에 렌더한다.
