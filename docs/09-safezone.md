## 1. 구역 — ABMEN 확정 풀화면 구성 (2026-09-19)

작은 락업과 정보·자막을 읽히게 유지하면서 전면 장면을 설계한다. 이전 상하 밴드·중앙 큰 로고의 좌표와 배색을 현행 디자인으로 되돌리지 않는다. 아래 수치 도입 이유와 과거 실패 사례는 이력으로 보존한다.

### 🔴 구역은 **머무는 자리**의 제약이다 — 궤적의 제약이 아니다 (2026-09-14 사용자 지시로 확정)

> *"모션 제한 건거 다 풀어. 모션영역 안에서는 **어떠한 모션도 허용**하고,
>  시그니처모션이나 크리에이티브를 위해서는 **모션영역 밖에서 안으로 들어오는 모션도 허용**"*

| | |
|---|---|
| **모션 영역 안** | **무엇이든 허용.** 크기·속도·궤적 제한 없다 |
| **밖 → 안 / 안 → 밖** | **허용.** 진입·퇴장·통과는 구역과 무관하다 |
| **금지** | 정보가 구역 **밖에 머무르는 것** — 플랫폼 UI 가 가리는 자리에 읽을 것을 두는 일 |

**2026-09-16: 시간만으로 정착을 추정하지 않는다.** `layout-scan`은 구역 밖 글자의 위치·크기가 같은 자리에 **0.5초 이상** 유지된 경우 하드로 센다(좌표 오차 2px). 움직이는 궤적과 의도적 가림은 화면 검토 후보다. `zone-check.sh`는 UI 영역 화소와 지속 시간을 **참고값**으로 보고한다. 0.5초 체류만으로 하드 실패시키지 않는다. 화소는 배경·장식·움직임·읽을 글자를 구분할 수 없기 때문이다. 실제 정보·락업·자막의 가림은 DOM 검사와 화면 검수로 판정한다.

**무대 y360~1360은 기본 배경과 정보 정착 영역이며, 전체 안무를 잘라낼 마스크가 아니다.** root의 전체 1080×1920 경계 외에 stage 래퍼 전체를 overflow:hidden/clip-path로 막지 않는다. 무대 밖으로 이동하는 객체는 전체 캔버스 레이어에 두고, 락업·자막의 z 순서와 실제 가독성을 확인한다. 사진 크롭·찢기·리빌 같은 개별 소재 마스크는 연출에 맞게 사용한다.

확대·회전·모프·겹침·마스크·블러·글로우·파티클·3D·이징·전환은 별도 승인 없이 선택한다. 제목 위치·배치·안쪽 여백·카탈로그 인용 수는 합불 기준이 아니다. 아래 과거 수치·배치 사례를 새 모션 제한으로 적용하지 않는다.

⚠️ **옛 문장을 걷어냈다.** 여기 원래 「scale·translate·그림자·글로우가 뻗은 자리까지 전부 이 상자
안이어야 한다」고 적혀 있었다. `docs/11-motion.md` 는 정반대로 「데드존은 글자가 머무는 자리의
제약이지 궤적의 제약이 아니다」라고 했다 — **정본 문서 둘이 서로 반대를 말하고 있었다.**
그 혼선이 컴파일러의 진입·퇴장 클램프로 굳어 이동이 죽었다 (`docs/02-pitfalls.md` §91).

`pipeline/zone-check.sh <p>`가 UI 인접 영역의 화소를 참고값으로, `node pipeline/layout-scan.mjs <p>`가 정보의 정착을 검사한다. 이미지·Canvas 내부 글자와 복잡한 마스크는 실제 화면에서 확인한다.

### 🔴 옛 표가 영역을 **43% 작게** 말하고 있었다

옛 구역표는 `브랜드존 y220~302 · 헤드존 y344~640 · 페이로드 y636~1340 · 자막 y1350~1450` 이었다.
디자이너가 「페이로드」를 캔버스로 읽으면 **704px** 뿐이다.

```
옛 페이로드   y636~1340   704px
2026-09-11   y360~1370  1010px   ← +306px (+43%)
2026-09-15   y360~1360  1000px 전폭   ← 자막 2줄을 받고도 면적 +19% (밴드 구조)
```

**헤드존과 페이로드를 나눈 게 문제였다.** 둘은 같은 캔버스이고, 그 안에서 무엇을 크게 둘지는
프레임이 정한다. 구역은 **플랫폼이 정하는 것**만 남긴다.

⚠️ 옛 표의 `자막 y1350~1450` 도 구현과 달랐다 — 실제 자막 필은 **1줄 y1360~1510 · 2줄 y1328~1545**
로, **2줄일 때 페이로드(≤1340)와 12px 겹쳤다.** 가운데 정렬이라 줄 수에 따라 위치가 튀었다.
→ 현행은 §5의 바닥 정렬·최대 2줄이다. 아래 옛 수치는 경과 설명이다.

## 3. 첫 화면의 위계

**0초 첫 화면은 포스터다** — 주제 제목·후킹(가장 큰 글자 = 볼 이유)·키 비주얼이 한 장에 완성돼 주제와 볼 이유가 읽힌다(2026-10-06 사용자 지시 · 정본 video SKILL 「최우선」 0.0초 포스터 행). 완성된 전체 표·조건 목록까지 0초에 넣으라는 뜻은 아니다. 큰 피사체의 변화·타이포·대비·사진의 근접 구도로 훅을 키우고, 나머지 핵심 정보는 의미 순서에 맞춰 정착시킨다. 주제 제목은 정보 정착 구역(x60~960·y360~1360)에 두고 로고 상자를 피한다.

헤드라인은 요점, 자막은 실제 발화다. 문구가 달라도 같은 의미를 향하고 강조 시각을 공유한다. “화면과 음성의 문장 중복을 줄인다”는 연출 시간을 분리하는 규칙이 아니다.

과거 이 절의 고정 리텐션 상승률·무음 시청률·저장 상승률은 이 채널에서 검증된 인과 수치가 아니므로 제작 합불 기준으로 쓰지 않는다. 실제 공개 후 결과는 영상별 README에 플랫폼·게시일·노출/조회 기준과 함께 기록한다.

## 4. 레거시 실사 전체 배경 프롬프트 사례 — 에셋 공통 규격 아님

당시에는 image2 의 2:3 이미지를 9:16 으로 잘라 썼다. 현행 이미지 생성(ChatGPT·Codex image_gen)은 9:16 을 직접 준다(941×1672 실측, `08-prompting.md` §1).
**두 단계로 좁아진다.**

```
1024×1536 (2:3 생성)  →  9:16 크롭에서 좌우가 잘림  →  그 안에서 다시 데드존
```

그래서 프롬프트에 이렇게 넣는다 — `cuts.json` 의 `style.framing` 에 들어 있다.

> **주요 피사체는 세로 55% 지점(화면 중앙보다 살짝 아래)에 두고 좌우에 여백을 남긴다.
> 상단 30%는 헤드라인 자리이므로 비운다. 하단 25%와 우측 12%에도 중요한 요소를 두지 않는다.**

**세로 55%인 이유**: 헤드라인 자리를 확보하면 콘텐츠 영역이 y 600~1450 이 되고,
그 중심은 y=1025 = 세로 53% 다. 처음엔 45%로 잡았다가 헤드라인을 빼먹은 걸 알고 고쳤다.

AI 에게는 픽셀보다 **비율과 방향**이 잘 통한다. `하단 25%를 비워라`가 `y>1490 금지`보다 낫다.

## 5. 자막 — 하단 밴드 안 · 바닥 정렬 · ≤2줄 (2026-09-15 개정)

```
바닥        y1540 고정 (하단 예약 380px)     ← 🔴 **바닥 정렬**. 줄 수가 달라도 바닥이 같다
글자        font 56px · line-height 1.25 · padding 14/20 · 크림 #F2E8D5 · **필(배경 상자) 없음** — 밴드가 딥그린이다
줄 수       **≤2줄** (2줄 h168 → 상단 y1372 · 1줄 h88 → y1452)
폭          ≤ 840px · 중앙(540) 정렬          → x120~960, 세이프존 우측 한계를 지킨다
청크 길이    **한 줄 14자 · 두 줄 26자 이하**   → 3줄은 무대를 먹는다
```

`compositions/captions.html` 의 `.cap` 이 이 값이다 — `left:120px;bottom:380px;width:840px;font-size:56px;line-height:1.25;padding:14px 20px;color:#F2E8D5` 에 `background` 없음.

### 왜 바꿨나 — 실측

| 문제 | 실측 |
|---|---|
| **가운데 정렬이라 줄 수에 따라 튄다** | 1줄 y1360~1510 · 2줄 y1328~1545. 바닥이 **35px** 달랐다 |
| **1줄일 때 너무 높이 뜬다** | 바닥 y1510 = 하단 예약 **410px**. 사용자가 실제 앱에서 「자막이 너무 위」라고 지적 |
| **2줄이 모션 영역을 먹는다** | 2줄 상단 y1328 이 옛 페이로드 하단(1340)과 **12px 겹쳤다** |
| **필이 세이프존을 넘는다** | 13자 한 줄이 x113~967 → 우측 **7px 침범** (버튼 열에 걸린다) |

(2026-09-11 판은 1줄 h149 로 강제해 모션 하단 1370 을 얻었다. 2026-09-15 밴드 구조에서 글자를 73→56 으로 내려
**2줄을 받고도** 무대 하단이 1360 이다 — 필을 없애고 밴드에 얹은 덕이다.)

### 구현

- `tools/fix-captions.mjs` — 긴 그룹 재분할 임계를 **12자**로 (기존 20자)
- `compositions/captions.html` — 필을 **바닥 정렬**(`bottom: 380px`)로, `max-width: 840px`
- 청크가 짧아지면 전환이 잦아진다 — **최단 노출 0.55초 하한**은 그대로 지킨다

⚠️ 한 줄이 12자를 넘을 수밖에 없는 고유명사(「축산물품질평가원」 8자 등)는 예외를 두되,
**폭 840px 을 넘으면 안 된다.** 넘으면 그 어절을 대본에서 줄인다.

### 자막을 더 올려도 되는 경우

훅 구간처럼 **큰 글씨 한 줄**이면 화면 중앙(y 800~1000)에 두는 게 더 잘 읽힌다.
어차피 데드존과 무관하고, 시선이 중앙에 있기 때문이다.

## 6. 점검 — 자동 검출과 실제 화면을 함께 본다

```bash
pipeline/zone-check.sh <프로젝트>          # 렌더된 MP4의 샘플 화소를 훑어 검토할 시각을 보고한다
pipeline/render-gate.sh <프로젝트>         # ②-e 로 위 검사를 포함한다
```

`zone-check`의 화소는 모두 검토 후보다. 장식과 이동 궤적을 읽을 정보의 고정 배치와 구분해 화면에서 판단한다:

| | |
|---|---|
| 플랫폼 상단 UI (y<220) 에 잉크 | 계정명·팔로우에 가린다 |
| 락업 띠(y220~350) 에 **락업 밖** 잉크 | 로고 옆에 뭔가 붙었다 |
| **키프아웃(y350~360) 에 잉크** | 로고가 눌려 보인다 |
| 무대 세이프존 좌우·상하 기본 여백 | 참고값. 배경·도형은 허용하며 글자의 정착은 layout-scan에서 검사 |
| 플랫폼 하단 UI (y>1540) 에 잉크 | 캡션·오디오 표시에 가린다 |

**CSS 를 읽어서 통과시키지 마라.** `scale`·`translate`·그림자·글로우는 CSS 좌표에 안 나타난다 —
00008 F01/F02 는 `top:360px` 인데 푸시인 배율 때문에 프레임마다 다른 자리에 그려졌다.

## 과거 자막 밴드 실측 — 현행 좌표는 §1·§5를 따른다 (2026-09-08)

HyperFrames `captionBand()` 의 기본값은 **화면 하단 1/6**, 즉 1920px 에서 **y1600~1920** 이다.
우리 최악값 하단 데드존은 **430px(y1490~)** 이라 **자막 전체가 데드존 안**에 들어간다.
무음 시청이 본체인데 자막이 통째로 안 보인다 — 조립 뒤 반드시 옮겨라.

```
자막 밴드   y1380 ~ 1485     (하단 경계 1485 = Reels 최악 데드존 1490 의 바로 위)
전경 한계   y  226 ~ 1360     (밴드 위 20px 완충대)
```

**밴드 높이는 105px 면 된다.** 판(pill) 없는 한 줄 크림 글자의 실측 잉크 높이는 **48px** 이다
(2026-09-08 실측). 스킬 기본값 320px 은 판·낱말 하이라이트를 쓰는 스킨 기준이라 우리에겐 과하다.
**밴드를 줄인 만큼이 그대로 모션그래픽 영역이 된다** — 사용자 지시: *"영역을 크게 쓰자."*

### 얼마나 내릴 수 있나 — 데드존이 정하는 한계

| 밴드 | 전경 한계 | Reels 최악(1490) | TikTok(1600) |
|---|---|---|---|
| y1280~1450 | 1260 | +40px | +150px |
| **y1380~1485 ← 현행** | **1360** | **+5px** | +115px |
| y1420~1525 | 1400 | **−35px 잘림** | +75px |
| y1470~1600 | 1450 | −110px 잘림 | 0px |

**Reels 하단은 자료마다 310~430px 로 갈린다.** 430(보수적)을 잡으면 밴드 하한이 1485,
310 을 잡으면 1610 까지 내려가 전경을 y1480 까지 쓸 수 있다.
**어느 쪽을 잡을지는 리스크 선택이지 계산이 아니다 — 사용자에게 물어라.**

⚠️ **프레임을 다 만든 뒤에 밴드를 옮기면 전경 재배치가 따라온다.** 2026-09-08 에 11프레임 중
**10개**를 손봐야 했다 — 워커들이 도구 기본값(전경 한계 y1580)에 맞춰 아래까지 꽉 채웠기 때문이다.
**프레임 작성 지시서에 y1260 을 처음부터 박아라.**

### 검산 — 눈이 아니라 픽셀로
```bash
# 완충대(1260~1279)에 전경이 있나 · 자막 줄이 색면 위에 얹혔나
# 0.5초 간격 전수 스캔이 12장 눈검사보다 확실하다 (2026-09-08: 80프레임 통과)
```
색면(골드 #F2C230) 위에 크림 자막을 얹지 마라. 관보레드(#8A1C1C) 위는 **7.63:1** 로
딥그린(7.50:1)보다 오히려 낫다 — 색면을 무조건 올릴 필요는 없다. **대비를 재고 판단하라.**

## 마지막 프레임이 검게 끝나면 안 된다 (2026-09-08 사용자 지시)

**숏츠는 반복재생이다.** 끝에 검은 프레임 한 장이 있으면 루프가 끊긴다.
루트 길이 끝에서 마지막 씬이 먼저 꺼져 호스트 배경(검정)이 드러나는 것이 원인이다.

```bash
# 검산 — 마지막 프레임 평균밝기가 0 이면 블랙이다
ffmpeg -ss <끝-0.1> -i <영상> -vf "scale=8:8,format=gray" -f rawvideo -
```
고치는 법: **마지막 씬 클립의 `data-duration` 을 루트보다 0.25초 길게** 잡는다.
`projects/00002-온누리적립/hyperframes/tools/safezone-fixups.mjs` 가 이 셋을 한 번에 처리한다
(자막 밴드 · 블랙 테일 · 자막 z-index). **조립할 때마다 돌려라** — 조립기가 기본값으로 되돌린다.

## 과거 큰 글자 실측 — 확대 금지가 아니라 배치 사례 (2026-09-08)

훅의 「20만 원」을 228 → **252px** 로 키웠더니 정지 상태 잉크 우측단이 x851 → **x947** 이 됐다.
우측 데드존이 x960 이니 **남은 여유가 13px** 이다. 여기에 배율 강조를 얹으면 —

| transform-origin | 최대 배율 |
|---|---|
| `left center` | **1.016** |
| `center` | **1.033** |
| `right center` | 1.070 (대신 좌측 60px 한계에 걸린다) |

**어떤 기준점을 잡아도 1.02~1.07 이다. 확대로는 강조가 안 된다.**
실제로 `left center 1.085` 로 두었다가 잉크가 **x1023** 까지 나가 63px 침범했고,
`center 1.030` 으로 낮춘 판본도 실측 **x959 — 여유 1px** 이라 자간·안티에일리어싱이
조금만 달라지면 깨지는 값이었다.

### 그래서 — 큰 글자는 **오른쪽으로 자라지 않는 수단**으로 강조한다

| 쓴다 | 쓰지 마라 |
|---|---|
| **왼쪽으로 이동** (강조가 강해질수록 우측단이 멀어진다) | 배율 확대 |
| **밝기**(`filter: brightness`) — 기하 변화 0 | 자간 확대 |
| **주변 후퇴** (조건·띠의 opacity 를 내려 초점을 모은다) | 우측 정렬 요소 추가 |
| **밑줄이 글자 폭까지 성장** | |

⚠️ **글자 크기를 올릴 때마다 우측 여유를 다시 재라.** 크기는 한 번 정하면 끝이지만
그 결정이 이후 모든 강조 수단을 제한한다.

### 🔴 폭은 추정하지 말고 **렌더된 잉크를 재라**

한글 글리프 폭은 폰트마다 추정과 크게 다르다. 두 프로젝트에서 독립적으로 같은 사고가 났다 —

- **00002**: 「20만 원」을 252px 로 키운 뒤 배율 강조를 얹어 잉크가 **x1023**, 데드존 63px 침범
- **00003(버거킹)**: **BMHannaPro 한글 글리프가 추정보다 넓어** 우측 데드존 침범이
  **세 프레임에서 독립적으로** 발생. 한 워커는 `document.fonts.ready` 를 스팬 생성 *전에* await 해서
  **폴백 폰트를 재고** 728.7px 를 633px 로 보고했다 (**15% 오차**) — 그대로 갔으면 금액이 버튼열에 걸렸다

```bash
# 렌더한 영상에서 실제 잉크의 최우측을 재라 — CSS 폭·추정치가 아니라 픽셀
ffmpeg -ss <시각> -i <영상> -frames:v 1 -pix_fmt rgb24 -f rawvideo - | <배경색이 아닌 마지막 x 찾기>
```
⚠️ 하네스로 잴 때는 **폰트 로드 완료를 텍스트 생성 뒤에 await** 해야 한다. 순서가 뒤바뀌면 폴백 폰트를 잰다.
