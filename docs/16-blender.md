# 16. Blender 3D — 오브젝트·건물 요소와 사진 매핑 (2026-09-27 개정 · 2026-10-06 실물 형상 대조)

**에이전트가 사람 손 없이 `blender -b --python`으로 모델링 → UV·텍스처 → 애니메이션 → 투명 렌더 → HyperFrames 합성까지 한다.** Blender 5.2.2 LTS(brew cask, `/Applications/Blender.app`), M1 Max에서 00006 v6·v7(온돌 F02~F04, 최종 `render-hf-v7-3d.mp4`)로 실제 적용·검증했다. 이 문서의 수치는 그 실측이고, 근거 없는 주장은 「미검증」으로 둔다.

## 1. 적용 단위와 선택 기준 — 요소 중심으로 적극 사용

**2026-09-27 사용자 지시:** video 기획에서 주연 오브젝트·건물 요소의 Blender 활용을 적극 검토하고, 형태·질감·동작·이해가 좋아지는 곳에 적용한다. 부산편 횟집 1·2층처럼 **공간 전체를 세트로 재현하는 방식은 비권장**이다. 개별 건물의 외관 모형은 활용 대상이며, 그 건물의 모든 방·가구·주변 거리까지 만들 필요는 없다. 이 절은 과거의 「3D만 가능한 공개」 조건과 「v7 룩 하나」 제한을 대체한다.

①②에서 사물별로 **무엇이 더 잘 보이는가**를 정한다. 회전·분해·결합·두께·가림 관계뿐 아니라 알아볼 수 있는 형태, 사진의 재질감, 주연의 존재감도 채택 이유다. 2D 구현 가능성이나 가격·제도라는 주제만으로 3D를 제외하지 않는다. 병·그릇·수납함·열차 부품·건물 외벽·지붕·창호처럼 실제 화면에 쓸 후보를 찾는다. 모형 수·비율·필수 컷 할당량과 기법별 승인은 만들지 않는다.

| 설명할 대상 | 권장 적용 단위 | 함께 쓸 재료 |
|---|---|---|
| 제품·음식·일상 사물 | 주연의 실루엣·두께·가동 부품, 회전·개폐·분해 | 사진/일러스트 UV, 포장·라벨 데칼, HTML 가격 |
| 건물·시설 | 외관 한 동 또는 필요한 외벽·지붕·창문·출입구·계단·바닥 단면. 🔴 실재 건물은 실물 사진 여러 장의 형상 사양부터(§4-1) | 면별 사진 매핑, 배경 사진/2D 도식, 포인터 |
| 1층에서 구입하고 2층에서 먹는 관계 | 층 도식과 이동 화살표, 생선·접시·계단 등 필요한 요소 | 층 번호·가격은 HTML. 식당 두 층 전체 인테리어 재현은 비권장 |
| 내부 구조·흐름 | 설명하는 부위의 단면·관·조립체 | 분리·투명도·흐름, 움직이는 HTML 라벨 |
| 위치·고도·지형 자체가 정보 | 설명 범위의 지형 조각 또는 지도 메시 | 확인된 고도·위성 자료, 사진/일러스트 텍스처 |

공간의 연결이나 규모 자체가 핵심이면 필요한 범위의 공간 3D도 선택할 수 있다. 카메라가 실제로 보여 주는 면·부위부터 구성하고, 설명과 무관한 방·도시·실내 소품까지 확장하지 않는다. **풀화면 합성은 유지하되 3D 제작 범위는 필요한 요소로 잡는다.**

README의 기존 `에셋 제작 경로`에 아래 결정을 짧게 남긴다. **3D가 이기는 곳**은 0~3초에 주연이 돌거나 갈라지거나 카메라가 주연 둘레·속을 지날 때(사진은 한 시점뿐), 두께·가동 부품·단면·층 관계가 설명 그 자체일 때, 건물·구조물의 형태가 정보일 때다. 음식·제품 주연은 실사로 보일 때만 3D, 아니면 사진풍(2026-09-29 사용자 — 00034). 사용하지 않으면 이 어느 경우도 아닌 이유를 **이 소재의 말로** 한 줄 — 「회전해도 새 정보 없음」·「층·단면이 없다」 같은 골격 공식은 이유가 아니다(2026-10-21 감사: 전 편 68줄이 같은 문장이었고 00051 뒤 3D 사용 0). 모든 후보의 기각표나 2D 대조 렌더를 의무로 만들지 않는다.

| 블록·대상 | 3D 범위·얻는 이점 | 표면·매핑·사진 출처 | 선택·검증할 것 |
|---|---|---|---|
| 작성 예: 건물 외관 | 외벽·지붕만, 기울며 건물 형태가 읽힘 | 사용 가능한 정면·측면 사진을 면별 UV로 | 3D+2D 배경, 측면 노출·창문 늘어짐 확인 |

실재 건물·구조물을 만들면 표 아래에 `실물 형상:` 줄을 쓴다(§4-1). 도식 3D뿐이거나 3D를 안 쓰면 `실물 형상: 해당 없음 — 이유`.

**룩과 사진 매핑:** 채널의 큰 사물·선명한 색면·Inter·작은 락업을 유지한다. 도식적인 부위는 v7의 팔레트 Emission·면 방향 명암을 재사용하고, 표면이 중요한 부위에는 사진·사용자 생성 이미지·일러스트 텍스처를 적극 입힌다. 사진 매핑에 사실적 조명은 필수가 아니다. `Image Texture → Emission`으로도 가능하며, 질감이 뭉개지면 면 명암을 약하게 하거나 외곽선을 생략한다(§5-1). 조명·PBR은 재질의 반사/굴절이 설명에 필요할 때 해당 요소에 검토한다. 장면 전체를 시네마틱 룩으로 바꾸거나 모든 효과를 켜는 것을 기본값으로 삼지 않는다.

3D는 HyperFrames 안의 알파 레이어로 합성한다. 제목·설명 라벨·자막·가격은 HTML, 제품 고유 포장·간판의 표면 글자는 검증된 원본 텍스처로 유지할 수 있다. 앞뒤 장면의 색·실루엣·주연 상태를 이어 준다. 한 장의 사진으로 보이지 않는 뒷면·내부가 복원되는 것은 아니다 — 회전 범위와 자료 범위를 함께 설계한다.

**과거 판정의 범위:** 00006은 2D v5 납품 후 3D v7을 시험했고, v7·B·C 비교에서 v7이 가장 낫고 조명판은 채널 컨셉과 맞지 않는다는 판정을 받았다(00006 output/review의 비교 시트 — 납품 뒤 정리돼 이 기기에는 없다). 이는 해당 장면의 룩 기록이며 사진 매핑의 금지가 아니다. 00016 F06은 부피 충돌은 3D, 휠체어·균열 가독성은 2D가 나았던 비교 사례다(00016 비교 시트(정리됨), 납품 v4 유지). 00030에는 사용자 요청으로 사진 매핑한 지형 소스가 있다(§2). 어느 사례도 3D의 흥행 우위를 증명하지 않는다.

## 3. 적용 전 구분할 것

- **캐릭터 리깅·표정 연기**: 미검증. 발·다리 같은 단순 부품 동작까지만 했다. 인물은 2D·생성 이미지가 현재 더 낫다.
- **사진 매핑과 AI 이미지→3D는 별개다.** UV 매핑은 준비한 메시의 표면에 이미지를 입힌다. Meshy·Tripo·Rodin·Hunyuan3D·TRELLIS는 조사만 했고 실행하지 않았다. 필요할 때 해당 서비스·모델의 현행 라이선스와 로컬 지원을 확인한다.
- **Three.js 실시간 경로(GLB → 브라우저 WebGL)**: GLB 내보내기는 되지만 HyperFrames 렌더의 WebGL 결정론(SwiftShader/GPU)은 검증하지 않았다. 현행 3D 는 **Blender 렌더 → 알파 영상** 경로만 쓴다. 평면 셰이더 효과(빛·색면·사진 표면)는 결정성을 실측한 WebGPU 번들로 쓴다(`docs/14-hyperframes.md` §16).
- **Blender MCP**: 공식 문서도 가드레일 없음·유출 위험을 경고한다. bpy 스크립트로 충분해 쓰지 않는다.
- **조명·PBR은 사진 매핑의 선행 조건이 아니다.** 00006 시험에서 실제 라이트·소프트 섀도·팔레트 툰·블룸·피사계 심도·모션 블러는 5.2.2에서 동작했고, 전부 켠 렌더는 약 2.8배였다(해당 시험값, 일반 배수 아님). 요소별 채택은 §1로 판단한다. EEVEE에는 Cycles와 같은 Shadow Catcher 기능이 없으며, 별도 그림자 합성 경로는 이 파이프라인에서 미검증이다.
- **§5-1의 카메라 투영·베이크·추가 PBR 매핑은 공식 기능을 조사한 제작 선택지다.** 공용 래퍼가 자동 설정해 주는 기능이나 모든 조합의 납품 검증을 뜻하지 않는다. 새 조합은 그 요소의 정지 화면과 실제 카메라 이동으로 먼저 확인한다.

## 4. 작업 루프 — 렌더 전에 숫자로, 만든 뒤에 눈으로

싼 정지 렌더로 형태·표면·카메라를 먼저 확인하고 기존 video ④⑤ 안에서 검수한다. 별도 3D 승인 게이트는 없다.

1. **설계(②)**: README에 §1의 대상·제작 범위·재질 경로를 적고 STORYBOARD에 동작·발화 정점·카메라 범위·HTML 글자 상자를 연결한다. 실재 건물·구조물은 §4-1의 실물 사진·형상 사양을 먼저 쓴다. 사용할 사진이 있으면 ①에서 확보한 원본을 먼저 연다. 새 텍스처가 필요하면 video ②의 기존 영문 프롬프트 형식으로 요청한다(§5-1).
2. **요소 시안(④)**: 실루엣용 최소 메시 → **`--review` 형태 시트**(Workbench 무작위 색 — 장면 카메라·정면·우측·위·3/4. 떨어진 조각·맞물림·비율이 색면으로 드러난다, 룩은 보지 않는다) → (실재 구조물은 §4-1 실물 대조 통과) → 대표 면에 실제 텍스처 → 시작·최대 회전·근접·정착 시각의 `--stills`. 모든 실행의 로그 첫머리 `ABM3D_QA`가 겹침(z-fighting)·뒤집힌 법선·어긋난 면 방향·음수 스케일(✗)와 떠 있는 조각·맞댄 면·중복 정점(△)을 숫자로 낸다 — ✗는 고치고, 동축 관의 progress 덧칠처럼 의도된 겹침은 `T.run(qa_ok=[("a","b")])`, 입자·공중 주연은 `ignore=`에 적는다(2026-10-22, §5 9번). 폭 360px 전체 화면과 원본 크롭에서 형태·이음선·해상도를 본다. 선택이 애매할 때만 같은 크기의 2D 대안과 비교한다. 모든 3D 장면의 이중 제작은 하지 않는다. 00016 F06은 첫 시점에서 유리벽이 주연을 가렸고, 스틸 3장 렌더 4초·시점 수정 포함 약 15분으로 비교했다(2026-09-24 실측).
3. **동작과 본 렌더**: `--preview`로 카메라 이동 중 매핑이 붙어 있는지 확인한다. `ABM3D_LAYOUT`의 bbox 교차는 실제 알파 윤곽·정보 가림으로 판정하고 `ABM3D_CAMERA`도 확인한다. 본 렌더는 1080×1920·60fps `.webm`과 `.anchors.js/.json`을 만든다. 게이트 B 시트는 이를 합친 실제 root에서 뽑는다. preview의 낮은 해상도·프레임 간격을 납품에 쓰지 않는다.
4. **합성**: 프레임의 `<video src="assets/3d/<장면>.webm">` 위에 HTML 정보·라벨을 얹는다. 라벨은 물체의 가장자리 앵커를 따르고 실제 글자 상자가 정보 정착 구역에 남도록 한다(pitfalls §119). 기존 납품 소스의 룩 시험은 세션 스크래치에서 하고 채택한 수정만 반영한다(§120). 보존 중인 2D·3D 판본과 자산은 지우지 않으며 매번 백업·대조판을 새로 만들지 않는다.
5. **검수(④⑤)**: 기존 `snapshot --at`·`layout-scan`·`still-scan`·번호 시트·렌더 게이트를 적용한다. 3D 픽셀은 DOM 검사에 잡히지 않으므로 실제 root/최종 MP4에서 회전 중 늘어짐·투영 이탈·알파 테두리·가는 무늬 깜빡임·라벨 가림·2D↔3D 전환을 직접 본다. 검수 역할과 최종 시각 판정은 공용 video 절차를 따른다. 사진 매핑 사용 여부나 모델 수 자체를 합격 기준으로 삼지 않는다.

### 4-1. 실재 건물·구조물 — 실물 사진 여러 장으로 형상 사양부터 (2026-10-06 사용자 지시)

> *"3d렌더링도 이번에 롯데월드타워 렌더링된거 봤는데 실제와 너무 달라 건물같은구조물은 실제 사진 여러장 분석후 렌더링 하도록 해주고"*

00051 타워는 높이 수치와 「테이퍼·초타원」 같은 글 설명만으로 단면을 로프트했고, 실물 사진과 같은 시점에서 나란히 본 적이 없었다. 대조해 보니 높이:밑폭이 실물 원경 사진(포디엄 위 보이는 부분) 약 5.3:1, 렌더 정면 스틸 약 7.4:1로 훨씬 가늘었다(pitfalls §176). 실재 건물·다리·탑·문·조형물처럼 이름으로 알아보는 구조물은 아래 순서를 지킨다. 도식 3D(단면·관·흐름)는 해당 없음이다.

1. **모은다(②):** `node pipeline/ref-photos.mjs <p> <refs-id> --search "<영문 이름>"`(Commons에 없는 시점은 WebSearch로 찾은 공식·보도 페이지 주소를 `--url`로). 후보 시트에서 대상이 아닌 것을 지우고 **서로 다른 시점 3장 이상**을 남긴다 — 정면에 가까운 원경(비율을 잰다), **영상의 카메라와 비슷한 시점**(내려다봄·올려다봄·3/4), 꼭대기·밑동 근경, 영상에 밤이 나오면 밤. 원경이 비율을 가장 덜 왜곡한다.
2. **사양을 쓴다(②):** README `실물 형상: <대상> · refs <id> · 사진 N장(시점) · 사양: …`에 높이·밑폭(① 확정 팩트·공식 자료 — 모르면 사진 비율만), **보이는 부분의 높이:밑폭**, 가늘어지는 모양(밑동·중간·위에서의 폭 비율), 평면 모양, 외피 무늬(세로선·가로띠·격자 간격), 꼭대기·밑동의 형태, 고유 디테일, **흔히 틀리는 것**(바늘처럼 가늘게·첨탑 추가 등)을 쓴다. 사진 비율은 정면 원경의 구조물 부분을 잘라 격자를 얹어 픽셀로 잰다 — `ffmpeg -i output/refs/<id>/NN.jpg -vf "crop=<w>:<h>:<x>:<y>,drawgrid=w=20:h=50:t=1:c=red@0.5" <스크래치>/m.png`를 열어 꼭대기·밑동 y와 높이별 좌우 x를 읽는다. 렌더는 알파 경계로 잰다 — `ffmpeg -i <스틸> -vf "alphaextract,bbox=min_val=40" -f null - 2>&1 | grep -o "w:.*"`(높이별 폭은 `crop=1080:4:0:<y>`를 앞에 붙인다).
3. **같은 시점으로 대조한다(④):** 장면 카메라에서 실물 사진과 가장 비슷한 시점의 시각들(정면에 가까운 시각 포함)을 골라 `--stills` → `node pipeline/ref-photos.mjs <p> <refs-id> --sheet output/3d/<장면>-stills/*.png`(한 번에 6장, 나눠 불러도 기록은 쌓인다). 별도 대조용 카메라 장면은 만들지 않는다 — 영상에 나오는 시점에서 실물과 같아 보여야 한다. 시트(위 실물·아래 렌더, 이미지마다 사분 격자)에서 실루엣 비율·가늘어지는 모양·꼭대기·외피를 사양과 한 줄씩 대조하고 어긋나면 메시를 고쳐 다시 찍는다. 최소 메시에서 먼저 통과시킨 뒤 텍스처·카메라 동작으로 가고, **본 렌더 직전 최종 소스로 다시 찍어 대조한다**. 결과는 README `실물 형상:` 아래 `실물 형상 대조: <refs-id> n/N 일치 — 어긋난 것`으로 남긴다.
4. **게이트:** 2026-10-06 이후 골격(`asset_prompt_format` 2)은 `stage-gate` ②가 `실물 형상:` 줄·사진 수를 경고로, ④가 하드로 본다 — 3D 스틸이 든 대조 시트가 없거나, 대조 뒤 장면 소스가 바뀌었거나, README 대조 결과가 없거나 n<N인데 이유가 없으면 막는다. 옛 골격의 진행 중 3D는 ④가 경고하며, 재제작·수정 요청을 받은 편은 cuts.json `asset_prompt_format`을 2로 올려 적용한다.
5. **룩:** 실재 건물은 실물과 같은 재질·색으로 만든다(사진풍 키 비주얼과 이어지게). 단색 v7 룩은 도식 3D용이다. 실물 사진은 분석 전용이다 — 텍스처로 쓰지 않고(외피 텍스처는 그 재질을 보고 생성 이미지로 요청한다, §5-1), 화면·문안에 출처를 쓰지 않는다.

## 5. 규칙 (근거: pitfalls §118, 공식 문서, 5.2.2 실측)

1. 형태는 bmesh 데이터 API로 만든다. `bpy.ops.*primitive*`·`transform_apply`를 쓰지 않는다(기본값이 위치까지 적용).
2. 코드로 준 부모의 역행렬은 단위 — 자식 location은 부모 기준 로컬이다.
3. 팔레트 색은 Emission + `Color.from_srgb_to_scene_linear()` + `view_transform='Standard'`. 사진은 Image Texture의 입력 색 공간을 맞추며 이 변환을 이중 적용하지 않는다(§5-1). 기본 면 명암은 월드 법선·고정 벡터 내적.
4. 5.x 애니메이션은 슬롯 액션 채널백(`animdata_get_channelbag_for_assigned_slot`)으로. 이징을 걸 키를 못 찾으면 예외.
5. 카메라 TrackTo는 `TRACK_NEGATIVE_Z`/`UP_Y`를 명시하고 구간 전체 `is_valid`를 확인한다.
6. 사라지는 물체는 alpha와 scale을 함께 0으로(외곽선 껍데기 제거).
7. 엔진 식별자는 `BLENDER_EEVEE`(5.0+). 문서 요약이 틀린 적이 있다 — 설치된 Blender에서 한 줄로 확인한다.
8. 시간: Blender k번 프레임 = 로컬 (k−1)/60초. 장면 길이 = round(길이×60) 프레임 = 프레임 슬롯 `data-duration`.
9. **같은 방향의 면을 같은 평면에 겹치지 않는다**(2026-10-22). 상자를 면끼리 붙여 조립하지 말고 한 메시로 만들거나 법선 방향으로 `ABM3D_QA`가 적어 주는 거리(물체 크기 중앙값의 0.2% — 4mm~20cm) 이상 띄운다 — 데칼 평면도 같다. 같은 자리의 두 면은 EEVEE가 프레임마다 다른 쪽을 그려 깜빡인다(z-fighting). 떨어진 조각은 닿게 하거나 `ignore=`에, 닫힌 메시의 법선은 바깥을 보게(`bmesh.ops.recalc_face_normals`). 외곽선 헐(`line=`)은 검사에서 뺀다.

### 5-1. 사진·일러스트 매핑 — 표면까지 완성한다

**메시가 형태·두께·가동 범위를, 텍스처가 표면의 색·무늬·사진 디테일을 맡는다.** 단색 블록아웃 뒤에 표면이 필요한 주연을 단색으로 끝내지 않는다. 사진 한 장을 평면에 붙여 움직이는 2.5D도 좁은 시점에서는 유효하지만, 옆면·실루엣이 드러나는 동작에는 그 부분의 메시와 이미지가 필요하다. 일반 사진 한 장을 입히는 작업과 다중 사진으로 형상을 복원하는 포토그래메트리는 구분한다.

| 대상·시점 | 매핑 방법 | 주의할 것 |
|---|---|---|
| 상자·외벽·지붕·문, 회전하는 제품 | **면별 UV / UV 펼침**. 정면·측면·윗면에 맞는 이미지 영역을 배정 | 사진의 원근과 메시의 원근을 이중으로 굽지 않도록 정면에 가까운 소스·보정본을 사용. 보이지 않던 면을 같은 정면 사진으로 복제하지 않는다 |
| 병·캔·포장 라벨 | **원통 UV**, 필요한 패널은 얇은 데칼 | 라벨 비율과 뒤쪽 이음선을 확인. 원통 옆면 매핑만으로 뚜껑·밑면이 해결되지 않는다 |
| 석재·목재·콘크리트 등 반복 질감 | **반복 UV 또는 Object 좌표의 Box 투영+Blend** | 실물 크기에 맞는 무늬 크기. Box 경계 혼합은 간판·창문·글자처럼 위치가 정확해야 하는 정보에 쓰지 않는다 |
| 사진 한 장의 외관, 제한된 카메라 이동 | **UV Project 카메라 투영**을 간단한 메시 위에 | 촬영 시점을 맞춘 고정 투영 카메라와 렌더 카메라를 구분. 저폴리 원근 투영 왜곡은 필요한 면만 분할. 투영 뒤쪽·가려진 면은 별도 자료/재질로 처리 |

위 방법은 [Image Texture](https://docs.blender.org/manual/en/latest/render/shader_nodes/textures/image.html)·[UV Project](https://docs.blender.org/manual/en/latest/modeling/modifiers/modify/uv_project.html)의 기능을 요소 제작에 적용한 선택 기준이다. 단일 사진에서 허용할 카메라 범위는 실제 시험으로 결정한다.

- **현행 도구:** `T.flat("facade", img=texture_path)`는 이미지를 읽어 Emission에 연결한다. 면 방향 명암 없이 사진색을 쓰려면 `steps=T.LIT`. 이것이 메시의 UV까지 만들어 주지는 않는다. `box/cyl/sphere`를 만들었다고 사진용 UV가 완성됐다고 가정하지 말고, 면별 loop UV 또는 투영 좌표를 장면 스크립트에서 지정한다. `tube()`는 자체 UV가 있다(2026-09-27 Blender 5.2.2 실행 확인: `box` UV 레이어 0, `tube` 1). 00030의 `UVMap`·Image Texture·마스크 혼합은 저장소 내 구현 참고다.
- **색과 표면:** 일반 색 사진은 파일의 색 공간(보통 sRGB), roughness·normal·height·별도 수치 마스크는 Non-Color로 읽는다. tangent normal은 일치하는 UV와 Normal Map 노드를 거쳐 BSDF의 Normal에 연결한다. 색 사진을 그대로 normal에 꽂지 않는다. **Emission의 색만 쓰면 normal/roughness를 추가해도 물리적 조명 반응은 생기지 않는다.** 실제 반사·요철이 필요할 때만 BSDF·조명을 선택하고, 사진에 이미 찍힌 그림자와 새 그림자가 겹치는지 확인한다. 팔레트 합성의 Standard 뷰 변환을 유지하고 실제 출력색을 본다.
- **움직이는 오브젝트:** 카메라 투영이 계속 재평가되면 물체가 움직일 때 사진이 미끄러질 수 있다. 붙어 있어야 하는 표면은 기준 자세에서 UV를 고정하거나 UV 텍스처로 베이크한다. 투영기를 물체와 함께 움직이는 방법도 가능하다. 베이크는 Cycles의 대상 UV·활성 Image Texture·이음선 margin을 설정하고 로컬 이미지로 저장한다. 색만 고정할 때는 Emit 또는 Diffuse의 Color만 사용하고, 움직이는 광원·가림 그림자까지 고정해 버리지 않는다. EEVEE 본 렌더와 베이크 단계는 별개다.
- **사진/생성 이미지 주문:** 기존 원본을 먼저 확인한다. 실재 건물의 외피·재질 텍스처는 §4-1에서 모은 실물 사진의 무늬·색·간격을 보고 요청한다(실물 사진 자체를 텍스처로 쓰지 않는다). 부족하면 video ②의 10라벨 영문 형식을 유지하며 `Use`에 UV texture/decal, `Composition`에 필요한 정면·측면·윗면/펼친 라벨과 비율, `Lighting`에 고른 재질 경로에 맞는 균일한 빛, `Constraints`에 불필요한 원근·하이라이트·그림자 제거를 구체적으로 쓴다. 반복 재질일 때만 seamless tile을 요청한다. 완성된 방·건물 전경 이미지를 모든 면에 늘여 붙이지 않는다. 사용자 생성 이미지는 실제 제품·건물의 증거를 대신하지 않는다.
- **로컬 보관·검수:** 실제 쓰는 이미지·마스크·베이크는 프로젝트 `assets/scene/` 안에 소스로 보관하고 장면 스크립트에서 로컬 경로로 읽는다. 공유 원본과 출처 처리는 ①을 따른다. 원본을 덮거나 삭제하지 않으며 출처·이용 조건·실제 사진/생성물 여부는 기존 README에 남긴다. 새 보고서·백업 폴더는 만들지 않는다. 시작·최대 회전·근접에서 UV 뒤집힘·늘어짐·이음선·뒷면·텍스처 누락과 데칼 z-fighting을 확인하고, 실제 root의 밝은/어두운 배경에서 알파 테두리를 본다.
- **에셋 장부 연결:** `cuts.json assets[]`로 추적하는 텍스처는 `file`에 원본 이미지, `render_file`에 실제 합성하는 `assets/3d/<장면>.webm`을 연결한다. 현재 `asset-state.mjs`는 원본/렌더 파일 지문과 HTML의 `render_file` 참조를 검사하며 Blender 내부 UV 연결은 검사하지 않는다. 최신 텍스처가 반영된 영상까지 보고 ④의 기존 accept 절차로 승인한다. webm 해상도 통과가 원본 텍스처의 확대 품질을 보장하지는 않는다. 검사 통과용 숨은 이미지 참조나 `reference-only` 표기로 우회하지 않는다.

### 5-2. 최적화 — 화면에 필요한 요소에 비용을 쓴다

EEVEE를 현행 본 렌더 경로로 유지한다. 엔진 교체나 옵션을 모두 낮추는 것보다 **모델링 범위·재사용·표면 표현**부터 줄인다. 아래는 공식 기능을 바탕으로 한 작업 지침이며 새 속도 개선 실측값은 아니다.

- 카메라의 전체 이동 범위에서 보이는 실루엣·단면·가동 부품을 먼저 만든다. 숨은 방·주변 거리·보이지 않는 미세 부품은 만들지 않되 반사·그림자·가림에 기여하는 부위는 남긴다. 돌출 창틀처럼 실루엣을 바꾸는 부분은 메시, 평평한 벽 무늬는 텍스처로 나눈다.
- 같은 창호·기와·의자·부품은 메시·재질·이미지를 공유한다. 반복 배열은 linked mesh/instances를 유지하고, 개별 형상 편집이 필요할 때만 실체화한다. Geometry Nodes 도입 자체를 의무화하지 않는다.
- 텍스처 크기는 **가장 가까운 카메라에서 그 면이 차지하는 픽셀과 UV 점유율**로 정한다. 가로 근사로 `원본 폭 × 해당 면의 UV 폭 비율 ≥ 화면에 보이는 면의 최대 폭`을 확인하고 크롭·사선 왜곡도 본다. 모든 요소에 고해상도 이미지를 붙이지 않는다. 경사진 표면은 EEVEE의 anisotropic filtering을 실제 프레임에서 비교하고, 먼 작은 무늬의 모아레·깜빡임은 해상도 증대만으로 해결하려 하지 않는다.
- 복잡한 정적 표면 연산은 필요하면 베이크해 재사용한다. 샘플·베벨·세분화·투명 레이어·반사·볼륨·DOF·모션 블러는 실제 보이는 개선에 맞춰 조정한다. `reset()`의 samples=16은 시작값이며 고정 품질 기준이 아니다. §2의 단색 장면 속도를 사진/PBR 장면의 예상 시간으로 단정하지 않는다.
- `--stills` → `--preview`로 결함을 모아 고친 뒤 본 렌더한다. 표면·메시·카메라·시간이 같으면 기존 3D 영상을 재사용한다. **앵커 좌표만** 달라졌으면 `--anchors-only`, HTML 가격·자막만 바뀌었으면 Blender 재렌더는 필요 없다. 카메라·물체가 바뀌었는데 앵커만 다시 뽑으면 안 된다. 납품 해상도·60fps와 실제 합성 검수는 유지한다.

## 6. 파일과 명령

```bash
pipeline/blender-render.sh <p> <장면> --review          # 형태 검수 시트 output/3d/<장면>-review/sheet.png (Workbench 무작위 색, 2026-10-22) + ABM3D_QA
pipeline/blender-render.sh <p> <장면> --stills 0,1.5,3   # 지정 시각 PNG + 레이아웃·카메라 검사 (ABM3D_QA_STRICT=1 이면 형태 오류에서 멈춤)
pipeline/blender-render.sh <p> <장면> --preview          # 540×960, 6프레임 간격
pipeline/blender-render.sh <p> <장면>                    # 본 렌더 → hyperframes/assets/3d/<장면>.webm + anchors.js/json
```

| 위치 | 내용 |
|---|---|
| `pipeline/blender/abm3d.py` | 공용 도구: `reset`·`flat(img=…)`·`pipe_material`·`outline`·`box/cyl/cone/sphere/tube/arrow`·`key/tween`·`camera`·`qa_check`(형태 QA — `run(qa_ok=)`)·`render_review`·`layout_check`·`export_anchors`·`run`. `styl`~`snow`는 과거 룩 시험 구현이며 채택 기준은 §1. 매핑·베이크 설정을 자동 완성하는 도구는 아니다 |
