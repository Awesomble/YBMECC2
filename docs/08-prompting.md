# 프롬프트 작성법 — 이미지 생성(GPT Image) · 클링/옴니(레거시)

**현행 이미지 에셋 요청의 형식 정본은 `.claude/skills/video/stages/2-architect.md` 「이미지 생성 요청」이다.** 영문 라벨 10개(생성)·4개(편집)의 고정 형식이고, `node pipeline/asset-prompts.mjs <p> --generate`가 형식을 검사한 뒤 사용자 ChatGPT 구독으로 로그인된 Codex CLI의 내장 image_gen으로 생성한다(2026-10-02). 이 문서는 **그 형식을 왜 그렇게 정했는지**를 남긴다. §2·§3은 레거시 실사 경로(`prompts.mjs`·image-to-video)다.

## 1. GPT Image 2.5 — 에셋 요청 형식의 근거 (2026-09-27)

### 왜 고정 영문 형식인가

ABMEN 요청은 처음부터 영문이었지만(`projects/*/README.md` 프롬프트 안 한글 0건) 대부분 한 문단이었고 라벨을 쓴 곳은 00014 하나뿐이라, 요청마다 빠지는 항목(빈 구역의 % 범위·조명 방향·투명 여부)이 달랐다. 여섯 편 모두 `1600×1600`~`3240×1500` 같은 픽셀 목표를 적었는데 그대로 나온 적이 없다. ABM도 같은 기간 네 형식(영문 라벨·한글 단락·한글 라벨)으로 갈렸다. 사용자가 영문 단일·동일 포맷을 지시했고(2026-09-27, ABM에서 정한 뒤 이식), 형식이 검사 가능해야 유지되므로 라벨을 고정하고 `asset-prompts --lint`(생성 전 `--generate`도 같은 검사)가 한글·라벨 순서·비율·픽셀 수·메타 줄을 검사한다. 사람이 읽는 선택 이유·사용 장면은 한글 메타 줄에 둔다.

### OpenAI 공식 가이드에서 가져온 것

[Image prompting](https://developers.openai.com/api/docs/guides/image-prompting)(GPT Image 2.5)과 [ChatGPT Images 2.5 발표](https://openai.com/index/introducing-chatgpt-images-2-5/)에서 확인했다.

| 공식 권고 | 형식에 반영한 자리 |
|---|---|
| 필요한 결과(용도)부터, 복잡하면 scene·subject·details·constraints로 나눈 라벨 절. 특수 문법보다 읽고 고치기 쉬운 형식 | `Use` 첫 줄 → `Scene`·`Subject`·`Details`… → `Constraints` 끝 |
| 재질·조명·색·매체를 적고, 사진이면 `photorealistic`을 말로. 넓은·저조도·시네마틱 장면은 분위기 단어 대신 **규모와 대기**를 서술 | `Details`·`Lighting`·`Color`·`Style` |
| 사람은 프레이밍·크기·시선·사물과의 접촉까지 | `Subject` 쓰는 법 |
| 편집은 `change only X` + 보존 목록. 한 턴에 한 변경. “same style as before”만으로는 유지되지 않으니 핵심 제약을 다시 적는다 | 편집 형식 `Edit`·`Keep unchanged` |
| 참조 이미지는 번호와 역할로 부른다 | 메타 `참조 첨부: Image 1 = … (역할)`·`Edit: Image 1 is …` |
| 투명 배경은 명시하고 받은 파일의 실제 알파를 확인한다(체크무늬를 그린 가짜 투명 주의) | `Output`의 투명 문장 · ④ 수령 검수 |
| 핵심과 무관한 장식 지시를 붙이지 않는다. 카메라 사양을 정확한 광학 시뮬레이션 요구로 쓰지 않는다 | 템플릿 아래 주의 문장 |

2.5가 발표에서 강조한 개선은 **요청한 곳만 고치는 정밀 편집·여러 턴의 편집 일관성·참조 사진 보존·투명 배경**이다. 그래서 같은 물체의 두 번째 상태는 새로 생성하지 않고 첫 결과를 편집한다 — ABM 00040은 첫 자물쇠를 참조로 붙여 둘째 장을 **새로 생성**했는데도 몸통 위치가 어긋나 합성에서 1.06배·24px를 보정했다. 편집 방식의 효과는 아직 미검증이다. 첫 적용 편의 결과를 여기에 적는다.

**API 전용 파라미터는 쓰지 않는다:** `quality`(low~max)·`size`(사용자 지정 해상도)·`background`·모델 선택(Flare·Sunburst). ChatGPT와 Codex 내장 image_gen 모두 비율과 투명 배경을 프롬프트 문장으로 요청한다.

### 생성 크기 실측 — 비율만 따르고 약 157만 화소

`projects/*/assets/`의 ChatGPT 수령 파일을 ffprobe로 셌다(2026-09-27). 2026-10-02부터 쓰는 Codex 내장 image_gen도 같았다 — 00042에서 1:1 → 1254×1254, 9:16 → 941×1672(편집 포함 7장). 그 생성기가 ChatGPT의 Image 2.5와 같은 모델 판인지는 확인하지 못했다. ABMEN과 ABM은 같은 ChatGPT 계정이라 함께 적는다. 00030은 `at least 2160x3840`(배경)·`2400x2400`(아파트)·`1800x3200`(소나무)을 적었지만 941×1672·1254×1254·941×1672로 왔다. 2.0과 2.5 중 어느 판에서 받았는지는 파일로 알 수 없으니 **새로 받을 때 다시 잰다.**

| 요청 비율 | 받은 크기 | ABMEN | ABM |
|---|---|---|---|
| 9:16 | 941×1672 | 3 | 11 |
| 2:3 | 1024×1536 | 0 | 5 |
| 1:1 | 1254×1254 | 3 | 21 |
| 4:3 | 1448×1086 | 0 | 9 |
| 3:2 | 1536×1024 | 0 | 7 |
| 2:1 | 1774×887 | 0 | 2 |

모두 약 1,572,000화소다. 그래서 요청에는 비율만 쓰고, cuts.json `min_width/min_height`는 이 크기 이하에서 표시에 필요한 최소로 적는다. 더 크게 보여야 하면 확대 폭·얕은 심도·크롭 범위를 바꾼다(ABM 00040 대문 배경은 확대 구간을 흐림본으로 덮었다). 9:16 전면 배경은 1080×1920에서 1.15배 확대된다. 옛 “9:16 프리셋이 없어 2:3에서 크롭” 우회는 폐기했다 — 9:16을 직접 받는다.

### 실물 대조 — 이름만으로는 일반형이 나온다 (2026-10-06)

사용자 지적: 「너무 사실성 없고 실제 이미지와 너무 달라서 현실감이 없어 — 리서치해서 실제 이미지 찾아서 재생성해」. 프롬프트에 대상의 이름과 몇 마디 묘사만 쓰면 모델은 그 종류의 흔한 모습을 그린다. 같은 날 00051의 3D 타워도 사진 없이 글 설명으로 만들어 실물보다 훨씬 가늘었다(pitfalls §176) — 원인이 같다. 그래서 실재 대상은 **실제 사진 3장 이상을 먼저 보고**(`ref-photos.mjs`), 현지인이 알아볼 **식별 특징**과 **흔히 틀리는 것**을 메타에 적어 `Subject`·`Details`·`Constraints`로 옮기고, 생성 뒤 실물과 **나란히 대조**한다(형식·명령: video ② 「실물 대조」). 공식 가이드의 「사진이면 photorealistic을 말로, 재질·조명을 구체적으로」를 실물 근거로 채우는 절차다.

실물 사진을 생성기에 **참조로 첨부하지 않는다.** 첨부한 사진의 구도·순간까지 닮은 결과가 나오기 쉽고, 그러면 남의 사진의 2차 저작물을 출처 없이 내보내게 된다(출처·저작자 표시 금지 — 2026-10-02·10-06). 사진은 형태·비율·재질을 읽는 데만 쓰고, 첨부(`참조 첨부`)는 우리가 만든 에셋·공식 원본에만 쓴다. 이 방식이 실물 일치도를 충분히 올리는지는 첫 적용 편에서 대조 시트의 식별 특징 n/N으로 기록한다(미검증).

### 이미지 안에 글자를 넣지 않는다

현행 모션 에셋은 영어 자막·라벨·숫자·정확한 수치를 전부 코드(Inter)로 얹는다. 2.5가 영어 글자를 잘 그리더라도 발화 동기·위계를 코드가 제어해야 하고, 틀린 글자를 고치려 이미지를 다시 받지 않기 위해서다. 글자를 비워 둘 면(간판·표지판·화면)은 `Subject`·`Composition`에 빈 면으로 적는다.

## 2. 레거시 — 실사 배경 image2 (`prompts.mjs`)

AI 실사 경로(보류)에서 배경과 화면 문자를 한 번에 그리던 규칙이다. 현행 모션 에셋에 적용하지 않는다.

### 화면 문자 — 문구는 지정하고, 그리는 건 맡긴다

**AI 가 문구를 지어내게 두지 않는다.** 세 번 갈아엎고 도달한 결론이다.

```
1차  글자 전면 금지            → 화면이 텅 비어 무슨 장면인지 알 수 없었다
2차  AI 에게 문구까지 맡김      → 엉뚱한 문장을 지어냈다
3차  글자 없이 뽑고 나중에 얹음  → 컷당 호출이 두 배. 자리가 안 맞는 사고도 났다
현재 문자열을 지정해 한 번에    → 컷당 1회. 틀린 컷만 편집으로 보정
```

`화면 문자` 줄에 **리터럴 문자열을 따옴표로** 지정한다 (`Include ONLY this text (verbatim): "..."`). 브랜드명·낯선 철자는 한 글자씩 떼어 적는다. 화면 문자는 지정한 짧은 문자열만 쓰고 설명은 자막이 담당한다. image-to-video 는 시작 이미지의 텍스트를 보존하므로(*"the model will preserve identity, layout, and text details"*) 한 번에 넣은 가격표가 영상 안에서 그대로 움직인다.

글자가 틀린 컷만 편집으로 보정한다. **보존 목록을 매번 다시 적는다.**

```
이 이미지를 편집합니다. 아래 문자만 추가하고 나머지는 전혀 바꾸지 마세요.
· "$12/yr"  —  좌측 카드 중앙, 큰 숫자 초록

구도·프레이밍·조명·색·기존 요소를 모두 그대로 보존할 것.
아무것도 이동·확대·축소·재배치하지 말 것.
```

**실제 상표·로고는 넣지 않는다.** 업체명은 자막이 담당한다.

### 톤은 주제의 정서를 따라간다

프리미엄해 보이려고 **딥 네이비 + 로우키**로 갔다가 갈아엎었다. 그건 럭셔리 브랜드 톤이지 **창업 정보** 톤이 아니다 — 어두운 방·새벽·로우키는 불안·고독·야근으로 읽혔고, 큰 창·오전 햇빛·밝은 화이트가 시작·가능성으로 읽혔다. **시청자가 어떤 상태에서 이걸 보는지** 생각하라. 경고·리스크는 대비를 높이되 어둡게 가지 않는다. 한 컷이라도 튀면 전체가 싸구려로 보이므로 컷 전체가 같은 공통 스타일을 쓴다.

`PROMPTS.md` 는 컷마다 한글·영문 프롬프트를 함께 낸다(레거시). 현행 이미지 생성 요청은 영문 단일이다(§1).

## 3. 레거시 — 클링 / 옴니(Veo) image-to-video

### 핵심 원칙 — 그림이 아니라 움직임을 쓴다

> *"describe the action and the camera, not the picture"*

**모델은 이미 시작 이미지를 보고 있다.** 거기 뭐가 있는지 다시 쓰면 글자만 낭비하고,
모델이 이미지와 프롬프트를 재해석하다 **룩이 틀어진다.**

```
❌ 어두운 배경에 황동 열쇠가 떠 있고, 카메라가 고정된 채 열쇠가 회전한다
✅ 카메라: 완전 고정. 이동·줌 없음.
   동작: 열쇠가 세로축을 중심으로 시계 방향 30도쯤 아주 천천히 회전하다 정면에서 멈춘다.
```

### 분량 — 60~100 단어

**너무 짧아도 안 된다.** 15단어짜리 한 줄로는 모델이 알아서 움직인다.
60~100단어로 **카메라·동작·빛 변화**를 나눠 적으면 결과가 눈에 띄게 안정적이다.

우리 프롬프트는 컷당 **73~78단어**다.

### 구조

| 줄 | |
|---|---|
| **카메라** | 움직임 · 렌즈감 · 속도 · **끝나는 지점** |
| **동작** | 이미지 안에서 **무엇이** 어떻게 움직이나. 안 움직이는 것도 명시 |
| **빛 변화** | 시간에 따른 밝기·하이라이트 이동 |
| 모션 강도 | `very subtle, nearly still` / medium / dynamic |
| 오디오 | 앰비언스. **대사·음악 없음** (나레이션은 우리가 따로 넣는다) |
| 길이 | 5초. **한 샷에 한 동작** |

**카메라를 맨 앞에** 둔다. 위치가 결과 안정성에 영향을 준다.

**끝나는 지점이 없으면 끝까지 움직이다 무너진다** — `~한 뒤 멈춘다`, `then settles and holds`.

**안 움직이는 것도 적는다.** "노트북은 움직이지 않는다", "위치는 그대로, 회전만" —
이게 없으면 모델이 멋대로 흔든다.

### ⚠️ 네거티브 프롬프트 — 빼먹지 마라

> *"Treat negative prompts as a quality filter, not an afterthought."*

클링에는 **별도 입력란**이 있다. 채우면 형태 뭉개짐(morphing)이 눈에 띄게 준다.
특히 움직임이 큰 구간에서 효과가 크다.

```
morphing, warping, melting background, object deformation, jittery camera,
sudden zoom, motion blur, flickering, text appearing, watermark, logo,
people, hands, extra objects, background shifting, unnatural physics
```

Veo(옴니)처럼 입력란이 없으면 프롬프트 끝에 `Avoid: ...` 로 붙인다.

### Veo(옴니)의 차이 — 오디오가 붙는다

Veo 3 는 **네이티브 오디오**(대사·효과음·앰비언스)를 함께 만든다. 4계층으로 쓴다:
**주체 → 카메라 → 오디오 → 길이**.

- **오디오 이벤트를 이름 붙여** 2개쯤 지정하면 화면에 맞춰 들어간다 (`발소리`, `종이 넘기는 소리`)
- **우리는 나레이션을 따로 넣으므로 대사가 생기면 방해다.** `대사 없음, 음악 없음`을 명시한다
- 프롬프트는 **영문으로** 쓰는 편이 낫다 — 시각 결과는 언어와 무관하다

### 그 밖에

- **처음부터 9:16 으로 생성한다.** 16:9 를 크롭하면 구도가 망가진다
- 클립은 **5~6초**. 어차피 2~3초마다 컷이 바뀐다
- **정적인 오브젝트일수록 모션을 약하게.** 과한 움직임이 곧 아티팩트다
- ⚠️ **옴니(Veo)는 우측 하단에 워터마크가 찍힌다.** 프롬프트로 못 막는다 — `docs/10-watermark.md`

### 쓰기 전 점검

- [ ] 카메라·동작·빛만 담고 있는가 (이미지 재서술 ❌)
- [ ] **60~100단어**인가
- [ ] **끝나는 지점**이 있는가 (`~한 뒤 멈춘다`)
- [ ] **안 움직이는 것**도 적었는가
- [ ] **네거티브 프롬프트**를 채웠는가
